### T9-1. README "Upgrading a testnet node" lists the two migrations in the wrong order
- **Severity (initial)**: Informational
- **Category**: Docs / Upgrade path
- **Location**: `crates/tn-reth/README.md:871-879`; `crates/telcoin-network-cli/src/node.rs:368-393`; `crates/node/src/lib.rs:80`
- **Claim**: The README says the first start "1. migrates the consensus database from MDBX to tndb ... 2. migrates the reth database from MDBX to tn-lmdb"; the code runs them the other way round: the `node` command opens the reth database (`open_execution_database`, node.rs:393 → `RethEnv::new_database` → `open_rw` → `check_backend` → `migrate::migrate_from_mdbx`) before it calls `launcher`, and only `launch_node` opens the consensus DB (`open_consensus_db`, lib.rs:80 → `tn_storage::open_db` → `migrate_from_mdbx`). The same order held in `v0.16.0-adiri` (node.rs:286 at the tag).
- **Failure scenario**: an operator who plans crash recovery or reads a first-start log by the README's numbering expects the consensus DB to move first. A crash between the two leaves `db/` on tn-lmdb (version 1002) with `consensus-db/` still MDBX, the reverse of what the list implies. Both halves are idempotent on the next start, so nothing is lost; only the description is wrong.
- **Key Question**: does any path open the consensus DB before `RethEnv::new_database`? (No: node.rs:393 runs before `launcher(builder, ...)`, and `launch_node` is the only `open_consensus_db` caller on the node path.)
- **PoC test**: a first start's log shows "migrated the reth database from MDBX to tn-lmdb" before "copied N rows of the consensus DB from MDBX to tndb".
- **Proposed fix**: swap steps 1 and 2 in the README (and in the e2e-oriented sentence "migrated both databases"), noting that the reth migration runs before the datadir's consensus DB is touched, which is why `db migrate-execution` can run alone. Docs only.
- **Relevant Files**: crates/tn-reth/README.md, crates/telcoin-network-cli/src/node.rs, crates/node/src/lib.rs, crates/storage/src/lib.rs
- **Source**: T9

### T9-2. The `mdbx` build's upgrade from `v0.16.0-adiri` has no rollback tripwire, and the README's Rollback text does not say so
- **Severity (initial)**: Low
- **Category**: Upgrade path / Docs
- **Location**: `crates/tn-reth/src/env/database.rs:119-130` (mdbx `open_rw`: reth's `init_db`, which writes/keeps reth's version 2), `:227-262` (mdbx `check_backend`: refuses only `tn-lmdb.dat` and the marker); `crates/storage/src/lib.rs:246-336` (`migrate_from_mdbx` deletes the MDBX consensus environments in every build; `reth-libmdbx` is a default feature, `crates/storage/Cargo.toml:66-67`, and resolves on in every release graph); `crates/tn-reth/README.md:954-968` ("Rollback. To `v0.16.0-adiri` ... what stops it is the version file") and `docs/src/getting-started/validator-operations.md:116-118` ("An earlier release refuses the migrated execution database before it changes anything, at the version file")
- **Claim**: On a `--features mdbx` build the reth database stays MDBX and `db/database.version` stays reth's 2, while the consensus-db migration still runs and deletes `consensus-db/{epoch,kad,cache}/mdbx.dat`. Started afterwards on that datadir, `v0.16.0-adiri` passes reth's version check (2 == 2), opens the MDBX reth database normally (the extra `Metadata["tn_storage_layout"]` row is a key reth v1.11.3 never reads), and then opens its consensus DB with libmdbx, which creates empty `epoch/kad/cache` environments: the node starts with no record of its votes and proposals, the equivocation hazard the README and the ops guide say the version file prevents. The tripwire is a property of the tn-lmdb build only (`TN_LMDB_DB_VERSION` is `#[cfg(not(feature = "mdbx"))]`); neither document scopes its rollback statement to that build.
- **Failure scenario**: a test or staging operator (the only users of the `mdbx` build: it is off in every release, `etc/backend-gate.sh`) upgrades a `v0.16.0-adiri` validator with the `mdbx` build, hits a problem, reads "the old binary refuses the migrated datadir before it changes anything", and starts the old binary in place without restoring the backup. It runs, with an empty consensus DB, in the epoch it voted in.
- **Key Question**: is there anything else in the `mdbx` build's first start that `v0.16.0-adiri` refuses? (I found none: `tn_storage_layout` is ignored by old reth; `consensus-db/tndb/` is a directory the old binary never looks at; node records are a network-level incompatibility, not a startup refusal.)
- **PoC test**: build the e2e binary with `mdbx` (`make build-e2e-bin-mdbx`), start a datadir on `v0.16.0-adiri`, restart it on the `mdbx` build (consensus DB migrates), stop, start `v0.16.0-adiri` again: it starts (no refusal) and `consensus-db/epoch/mdbx.dat` is a fresh file.
- **Proposed fix**: smallest: in both documents, state that the version-file tripwire exists only on the default (tn-lmdb) build, and that an `mdbx`-build upgrade leaves `v0.16.0-adiri` free to start on the migrated datadir with an empty consensus DB. A code-side option, if wanted: have the `mdbx` build's `open_rw` also record a TN version in `database.version` (e.g. 1000 + 2 with a different offset) and accept it, so the old binary's `check_db_version_file` refuses there too; that touches only the open path. Since the `mdbx` build ships in no release, docs alone are proportionate.
- **Relevant Files**: crates/tn-reth/src/env/database.rs, crates/storage/src/lib.rs, crates/tn-reth/README.md, docs/src/getting-started/validator-operations.md
- **Source**: T9

**Q3, determinism: every environment, clock, thread-count or host read in the new code, and what it can change.**
- `TN_PARALLEL_STATE_ROOT`, `TN_PARALLEL_ACCOUNT_WALK`, `TN_PARALLEL_STORAGE_WALK` (parallel.rs:208-230, account_split.rs:94-110, storage_split.rs:107-123; `OnceLock`, read at the first block): select which code computes the root. The root is the same by construction (the split composes reth's own `StateRoot`/`StorageRoot` over nibble-restricted cursors) and checked on blocks `number % 256 == 0` (`block_is_checked`, parallel.rs:246-252, by block number so every node checks the same blocks; a mismatch uses the serial result). Consensus-visible only if the parallel code is wrong, which the README states with its operator response (README:92-105). An operator who sets the switch on one node changes nothing absent a bug. Not a finding.
- `rayon::current_num_threads().min(WALK_HELPERS)` (parallel.rs:381) and the CLI's `available_parallelism` pool (node.rs:283-291): the number of helper jobs; the subtrie and storage pieces are keyed by nibble and their union is composed by the caller, so which thread worked a piece cannot change the root. Timing only.
- `TN_PARALLEL_STATE_ROOT_SHADOW`, `TN_EXEC_CACHE_SHADOW/STATS`, `TN_EXEC_CACHE_{ACCOUNTS,SLOTS,CODE}`: test builds only (above).
- The execution cache (exec_cache.rs): fixed capacity in release builds (`CacheCapacity::default`, :191-200); a hit returns the value the parent state holds by the module's invariant (:21-57), so capacity and eviction change hit rates, not values. Its stale-hit check samples by a per-node hit counter (`hit.is_multiple_of(CHECK_ONE_HIT_IN)`, :636), not by block number as the state-root check does; under a stale-hit bug the checked node repairs its block while others do not, but the cache's buckets are seeded per process (foldhash `RandomState` through alloy's `DefaultHashBuilder`), so hit sets already differ per node and a stale value would already fork them. Noted, not a finding: both are bug-contingent and the README's "Checks" paragraph describes the behaviour.
- `--db.gap-fill auto` (tn-lmdb `fill_gaps`, env.rs:1171-1250): the auto width is chosen from measured sync costs (timing) and each gap is read through the file and written back from that buffer at the same offset: "rewriting a page with its own bytes" (:1185-1202). Bytes on disk and the file's size are unchanged; `Resident::Unsupported` turns it off with a warning. Timing only.
- `--db.read-transaction-timeout` (database.rs:744-750; tn-lmdb-reth timeout.rs): a marked read transaction's later calls fail with `ReadTransactionTimeout`; a failed read during a build is an error that drops the cache and fails the block (fail-stop), never a different value. The export and the migration opt out.
- `Instant::now` in execution.rs (:213, 385, 438, 576, 943, 982, 1099) and output_overlay.rs (:270, 299): stage histograms only. `SystemTime::now` in `record_client_version` (database.rs:916-927): the key of a `VersionHistory` row, node-local metadata, not in the state root, not exported in the state pack. `SystemTime::now` in `reset_execution` (:160-166): the reset directory's name. The boot record (tn-lmdb `boot_record.rs`): decides only whether the open drops the page cache.
