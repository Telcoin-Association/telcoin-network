## Answers to the brief's questions (the evidence the findings and rejections cite)

### Q1. What is cached, keyed by what, invalidated by what
- Three fixed-size direct-mapped tables (`exec_cache.rs:303-322`): `accounts: Address ->
  Option<Account>` (`None` = does not exist), `storage: (Address, StorageKey) -> StorageValue`
  (zero = unset), `code: B256 -> Bytecode`. Block hashes are NOT cached (`block_hash` passes to
  inner, `exec_cache.rs:866-878`); neither are hashed-key storage reads (763-769), roots or
  proofs. The whole cache is keyed by one anchor block hash (`SavedCache.hash`, 414-419).
- Fills: a miss fills from the parent state (`basic_account` 731-734, `storage` 757-760,
  `bytecode_by_hash` 782-787; a `None` bytecode is not cached). After a successful build the
  block's own `BundleState` (the one persistence writes: `execution.rs:481-485`, `db.take_bundle()`
  at 443) moves every changed entry forward (`insert_state`, 365-409) and re-anchors at the new
  hash (`check_in_execution_cache`, 488-502).
- Invalidation: any parent other than the anchor gets a fresh empty cache (`check_out_execution_cache`
  472-481); a failed build never checks in (`execution.rs:333-339`), a failed persist clears the
  saved cache (`persist_executed_output`, 555-559), a refused bundle (`WipedSetFull`,
  `ModifiedWithoutInfo`) drops it (494-498), a stale checked hit drops it with the code table
  (512-519). Only the `keccak256(code) -> code` table survives a drop (504-510).
- Writers that could change a cached value: a block's bundle (applied); a persist (does not
  change state at any block hash); SELFDESTRUCT / EIP-161 removal of an account that existed at
  the anchor (`was_destroyed() && original_info.is_some()` → wiped set, account entry removed,
  376-385; later reads of its slots bypass the cache, 745-748; later bundles never fill its slots,
  400-405); a slot zeroed (inserted as `U256::ZERO`, read back as `None`, 755); epoch-close
  system calls and the adiri fork swaps (all through `self.evm.db_mut().commit(..)` on the revm
  `State`, `block.rs:484, 913, 1052, 1493, 1778, 1818`, so in the bundle); snapshot restore,
  `db reset-execution`, `db migrate-execution` (separate processes, `telcoin-network-cli/src/db.rs`;
  the restore also refuses a datadir past genesis, `snapshot.rs:563-581`); a restart (the cache is
  process memory, `ExecutionCacheSlot::new` at `env/mod.rs:233`).
- Wiped account, slots read before the wipe in the same block: they were filled from the parent
  state and stay in their buckets, but the address is in the wiped set from `insert_state` on, so
  every later read bypasses (`is_wiped` first, 745). Slots never read: not in the cache, bypass
  anyway. Both pinned by `wiped_account_slots_read_the_state_not_the_cache` (plants the entry by
  hand, storage v1) and `wiped_existing_account_keeps_the_cache`.
- Recreated account (CREATE2 at a wiped address): same block → status `DestroyedChanged` with
  `original_info` set, so the wiped branch runs (account entry removed, address wiped, new info
  not cached; the next read misses to the parent, which is the post-block state); a later block →
  `InMemoryChange`, the account entry is inserted, the slots are skipped because `is_wiped`
  (400-405), so reads bypass forever (`create2_over_a_funded_address_keeps_the_cache`). An
  account created and destroyed in the same block with `original_info == None` loses its listed
  slots and its account entry (386-393); no unlisted slot of it can be in the cache because revm
  never asks the database for the storage of a `LoadedNotExisting`/`InMemoryChange`/destroyed
  account (`is_storage_known`, revm `State::storage`), and the only other source of entries is a
  bundle of an account that exists after its block.
- Parent-state correctness for the bypass: the memory overlay answers a wiped account's unlisted
  slot with `Some(0)` (`memory_overlay.rs:218-222` → `BundleAccount::storage_slot`, which returns
  zero whenever `is_storage_known`), and the database has the wipe after persist.

### Q2. Determinism, the sampled checks, RPC
- A hit returns the cached value; a miss the parent's. The check (`is_checked`, 630-637) samples
  by the cache's own per-table hit counter (`hit.is_multiple_of(256)`, counter value before the
  increment), NOT by block number, so every node checks different hits. On a mismatch the read
  returns the fresh value, the error log carries the key and both values
  (`check_account`/`check_storage`/`check_code`, 658-718), `tn_reth.exec_cache_stale_hits_total`
  increments, `served_stale` is set, and `build_recovered_block` discards the attempt (block or
  error), drops the cache with its code table and builds once more with no cache
  (`execution.rs:330-353`); a stale hit on the rebuild is impossible (no cache) and returns
  `ExecutionCacheStaleOnRebuild`. The node does not stop. With `TN_EXEC_CACHE_SHADOW=1` (test
  builds only: `cfg(any(test, feature = "test-utils"))`, and `tn-reth/test-utils` is a
  dev-dependency of `telcoin-network-cli`, resolver 2, so the release binary has no shadow/env
  knobs) every hit is checked and a stale one panics.
- The check cannot itself cause divergence: on a match it returns the cached value, on a
  mismatch the attempt is thrown away. Node-to-node divergence needs a stale hit that is not
  checked, i.e. an invariant failure; see T4-rejected-2 for why per-node sampling is not worse
  than block-keyed sampling here.
- RPC: `CachedStateProvider` is constructed only in `build_recovered_block`
  (`execution.rs:322, 347`); RPC, `eth_call`, tracing and the pool validator read
  `BlockchainProvider` directly. The slot is behind `parking_lot::Mutex` and a build owns its
  `ExecutionCache` by value (`check_out` moves it out), so no two threads share one table; the
  provider is only read by the single-threaded revm `State` (the state root takes the plain
  provider, 429-436). fixed-cache's "insert into a locked bucket is dropped" hazard therefore
  cannot occur.
- fixed-cache internals verified: `get` locks a bucket only when its tag equals the key's full
  high-bit tag and then compares the full key (`get_inner`), so a collision is a miss, never a
  foreign value; `insert` overwrites (drop of the old `Bytecode` value when `NEEDS_DROP`);
  `remove` unlocks to tag 0; `TopBitHash` sets bit 63 so no live tag is 0 (the test
  `top_bit_hash_keeps_an_empty_bucket_from_matching_the_zero_key` shows the hazard without it).
  `Cargo.toml:261` pins `=0.1.8`.

### Q3. The "pin", error paths, memory bound
- The "pin" in the branch description is the dependency pin (`fixed-cache = "=0.1.8"`, the
  module docs list which internals it relies on). There is no pinned provider: a build *checks
  out* the cache (the slot holds nothing meanwhile, 462-484) and checks it in only after the seal.
  A build error keeps the code table (`execution.rs:335-337`); a panic unwinds the local
  `exec_cache` (nothing is checked in; parking_lot does not poison); a persist failure clears the
  saved cache; an engine abort halts the node (`engine/src/lib.rs:362`) and the next process
  starts empty; an epoch boundary keeps the same `RethEnv` (created once in
  `node.rs:915/1813` before `run_epochs`), so the first block of the next epoch finds the cache
  anchored at the closing block.
- Memory: bucket counts are fixed (2^18 + 2^20 + 2^12 buckets of 128 B = 160.5 MiB, lazily
  touched), the wiped set is capped at 4096 (then the cache drops, 382-383), the code table
  holds at most 4096 bytecodes (EIP-170 applies to every create but the pre-genesis registry
  build, `genesis.rs:358`). A workload of many distinct slots only evicts; it cannot grow
  anything. The cheapest forced drop is 4097 wipes (about 240M gas, module docs 71-75) or a
  stream of anchor mismatches, both performance only.

## Considered and rejected

1. **Stale account value from code-hash normalisation.** A cached account can come from the
   bundle (`Account::from(info)`, 406) or from the provider (`basic_account`, 733); one could
   carry `Some(KECCAK_EMPTY)` and the other `None`. Both reach revm through
   `StateProviderDatabase::basic_ref` → `Into<AccountInfo>`, which maps `None` to `KECCAK_EMPTY`,
   so the EVM sees one value; `check_account` compares through `get_bytecode_hash()` (665) for
   the same reason. Holds.
2. **Per-node sampling (hit counter) instead of block-number sampling.** The README insists
   on block-keyed sampling for the parallel root so "nodes running the same code always publish
   the same root, right or wrong". For the cache this does not transfer: a stale entry can only
   exist after an invariant failure, and whether a given node *hits* it depends on that node's
   eviction history, which is seeded per process (`DefaultHashBuilder`, 889), so stale hits are
   already non-deterministic across nodes; per-node sampling adds detection coverage and never
   changes a correct read (a match returns the cached value, a mismatch discards the attempt).
   Not a determinism defect; the docs say "one hit of each kind in 256" and do not claim
   block keying.
3. **Node continues after a stale hit instead of fail-stopping.** The rebuilt block is the
   uncached one (the proptest and `stale_checked_hit_rebuilds_the_block_without_the_cache`
   pin it), the counter is alertable, and the same continue-with-the-safe-result policy is the
   one the parallel-root check uses. Stopping would not repair an earlier unchecked block
   either. Design choice, documented at `exec_cache.rs:79-85`; recorded in T4-1 as a docs gap.
4. **Two concurrent builds on one env sharing a cache.** `check_out` moves the saved cache
   out under the mutex (463-470); a second concurrent build gets a fresh one. Each build owns
   its tables; the last check-in wins and is anchored at its own block. No sharing, no fixed-cache
   dropped-insert hazard. Only tests build concurrently anyway (the engine is one blocking task).
5. **Rollback of a multi-block output leaves the cache anchored at a rolled-back block.**
   `rollback_in_memory_output` removes the in-memory blocks, the engine returns an error and the
   engine task halts (`engine/src/lib.rs:362`); any later build on the pre-output parent would
   find the anchor ≠ parent and start empty (472-481; `discarded_block_then_another_on_the_same_parent`,
   `sibling_block_starts_empty`). State at a block hash is immutable (no reorg, header commits
   to the post-state), so even a surviving anchor would be correct for a child of that hash.
6. **Persist retry succeeding after a cleared cache.** Attempt 1 clears the saved cache,
   attempt 2 commits; the next output starts empty on its parent. Performance only
   (`persist_fail_then_retry_then_continue`).
7. **Adiri fork swaps bypassing the bundle.** `apply_consensus_registry_fork`,
   `apply_worker_configs_fork`, `apply_governance_safe_fork` all end in
   `self.evm.db_mut().commit(EvmState)` with `AccountStatus::Touched` accounts
   (`block.rs:896-913, 1035-1052, 1320-1338, 1452-1493`), which revm turns into transitions, so
   the bundle (and therefore both persistence and the cache) carries them; pinned by
   `fork_boundary_close_builds_through_the_cache` (adiri builds).
8. **EIP-161 clear of a genesis-empty account with storage (v1 only).** Status
   `LoadedEmptyEIP161` → `Destroyed` with `original_info` set, so it is wiped (376-385); the
   test `wiped_account_slots_read_the_state_not_the_cache` plants the hazardous entry and reads
   through the bypass.
9. **The zero key / zero tag hazard of fixed-cache** (an all-zero key whose hash has zero high
   bits reads an empty bucket). `TopBitHash` sets bit 63 (905), which is inside `tag_mask` for
   every power-of-two capacity below 2^63; `Bytecode` values carry `ALIVE_BIT` anyway. Test
   present.
10. **`insert_state` iteration order over `bundle.state` (a HashMap).** Writes go to distinct
    keys; a bucket collision between two accounts evicts one (a later miss), and `remove` is a
    no-op on a bucket holding another key, so no order produces a stale read.
11. **`is_multiple_of(256)` with `hit == 0`.** The first hit of each table is checked; after a
    drop the counters restart, so a frequently dropped cache is checked slightly more often.
12. **`best_block_number()` on a fresh datadir.** `init_genesis` writes every stage checkpoint
    at 0 and `save_blocks` upserts `Finish` in the blocks' transaction, so `finalized == tip` at
    genesis and after every clean commit; a marker ahead of `Finish` can only come from a
    datadir that lost blocks, which is the error the heal already reports.
13. **`BlockState` drop loop.** `Arc::into_inner` consumes this owner's reference and hands
    the parent to exactly one releaser; a shared parent is left to its last owner, which runs the
    same loop on its own drop. Test `deep_chain_drop_preserves_shared_tail` covers shared and
    unshared tails; the TN-0052 ledger entry matches the code.
14. **Rebuild side effects.** The discarded attempt touched only metrics, logs, the
    cache (dropped) and a `State` that is dropped; `epoch_close_gas` is per executor; the
    overlay is extended only in the seal (`execution.rs:307, 479`).
