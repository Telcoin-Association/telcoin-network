## Answers to the brief

### Q1. Do the tasks, the sixteen account subtries and the sixteen storage pieces compose the serial result?
No counterexample found; the argument, with the lines it rests on:

*Same view.* The walk and every task build their cursor stacks through one helper,
`layered_factories` (`output_overlay.rs:154-171`): `current` over `runs` over the database, for
both the trie and the hashed cursors. The walk uses it at `parallel.rs:353`, a storage-root task at
`parallel.rs:551`, a helper at `parallel.rs:502`. The runs and `current` are borrowed by reference
inside `rayon::in_place_scope` (`parallel.rs:362-414`); no task can see a later block's overlay
because the overlay is extended only after `finish` returns (`execution.rs:424-436`, then
`seal_executed_payload`). Each task reads its own read-only transaction (`parallel.rs:496-497`,
`545-546`), opened after the walk's; nothing commits between them on the node path (the engine
builds every block of an output, then persists in line, `execution.rs:560-596`), and each task
compares `ChainState::LastFinalizedBlock` with the walk's (`parallel.rs:498-501`, `547-550`,
`snapshot_tip` 533-535); the persist writes that marker in the same transaction as the blocks
(`execution.rs:582-590`). A task that sees another tip fails (`TaskError::TipMoved`) and the walk
computes that root on its own transaction (test `moved_tip_falls_back_to_serial`,
`parallel_tests.rs:318-348`; `moved_tip_leaves_the_subtries_to_the_walk`,
`account_split_tests.rs:547-571`; `moved_tip_leaves_the_pieces_to_the_walk`,
`storage_split_tests.rs:496-518`). An account whose info changes in the block while its storage root
runs on a task is no hazard: the task reads only the storage tables and `current`'s storage of that
address, and the walk encodes the leaf from the hashed account cursor (`trie.rs:489-493`).

*Storage-root tasks (whole tries).* A task runs reth's own `StorageRoot::root_with_updates` over the
walk's factories and the target's prefix set (`parallel.rs:554-559`); the serial walk runs
`calculate_with_cursors` over the shared cursors with the same prefix set (`trie.rs:316-337`), and
the shared cursors are repositioned by `set_hashed_address`, which resets every layer
(`in_memory.rs` and `post_state.rs` `set_hashed_address` → `reset()`; TN's `cursors.rs:148-153`,
`207-213`; `storage_cursor.rs:130-134`). The hook takes the task's result in place of the call
(`trie.rs:310-314`) and processes it identically (`process_storage_root_result`, 472-495). Wiped
storage: `PrefixSet::is_empty` is false for an `all` set (`prefix_set.rs:244-246`), so a wiped
storage gets a task with the `all` set (`parallel.rs:518-529`), same as the walk's `unwrap_or_default`
would give; it is never split (`wants_split` refuses `all`, `storage_split.rs:129-131`). Destroyed
accounts get no task (`parallel.rs:523`); the walk meets no leaf, and `finalize` marks their storage
tries deleted (`updates.rs:153-156`). An emptied storage (every slot zero, account kept): the task's
`is_storage_empty` short circuit returns `(EMPTY_ROOT_HASH, 0, deleted())` (`trie.rs:771-779`),
exactly what the walk would have computed; `OverlayStorageCursor::is_storage_empty` consults the
complete overlay first (`storage_cursor.rs:106-128`), the same cursor type in both paths.

*Account subtries.* Each subtrie is reth's `StateRoot` over `Subtrie` factories restricted to one
first nibble (`account_split.rs:278-294`). The restriction is applied at the outermost cursor layer
(`SubtrieCursor` wraps the whole stack, 356-415), so the layered cursors below see a monotone
sequence of seeks clamped to `[n]` (`seek`: `key.max(start)`, 464-466; nybbles `Ord` is
lexicographic with a shorter prefix first, `nibbles.rs:158-178`) and keys outside `[n]` read as the
end (445, 475, 490, 495). `seek_exact([])` returns `None` without touching the inner cursor (454-457),
so the walker starts with an empty root subnode as the serial walk does when no root node is stored
(`walker.rs:243`, 234). The serial walker reaches nibble `n` by `move_to_next_sibling` on the root
subnode → `consume_node` → `seek([n])` (`walker.rs:363-366`, 301-331); the subtrie walker's first
`consume_node` seeks `[]`, clamped to `[n]`: the same stored node, and `stack[0].set_nibble(key[0])`
(311-313) puts the root subnode at `n` in both. From there both walkers see the same cursor answers
until the subtree ends; the subtrie's `seek([n+1])` reads as `None` and clears the stack
(`walker.rs:302-306`). The node iterator's hashed seeks are the same keys (the first one, `[]`
packed, is clamped to `n<<4`), and a seek is never behind the cursor (seek keys are monotone,
`next_unprocessed_key`, `walker.rs:161-169`). Node `[n]` carries no `root_hash` (only `len == 0`
nodes do, alloy-trie `hash_builder/mod.rs:452`) and the root is not stored, so `[n]` is never
skipped in either walk (`update_skip_node`, `walker.rs:172-194`): both rebuild it from its children.
The prefix sets are cut by first nibble (`account_split.rs:168-197`); every account prefix-set key is
a full 64-nibble hashed address (`HashedPostState::construct_prefix_sets`), so no entry straddles the
boundary, and `PrefixSet::contains` answers the same for every prefix under `[n]` (keys outside
`[n]` never start with such a prefix). Storage prefix sets and destroyed accounts go whole to their
address's nibble (182-187), so each account's storage root and `deleted` marker come from exactly one
subtrie.

*Composition.* A subtrie whose keys all start with `[n]` hashes to an extension `[n]` over the node
at `[n]`; `compose` (`account_split.rs:298-325`) rebuilds that node from the subtrie's own update
for path `[n]` when `hash_mask == state_mask` (`child_node`, 338-354) and checks the rebuilt
extension against the subtrie root (351-353); the block root is the branch over the sixteen nodes
(`branch_root`, 329-333), which is what reth's hash builder computes for a root branch
(`push_branch_node` + `current_root`). The reconstruction is exact because alloy-trie sets a parent's
hash-mask bit exactly for a child that is a branch (`store_branch_node`, `hash_builder/mod.rs:428-433`;
a skipped branch via `add_branch`, 311-312) and clears it for an extension (`update_masks`, 460-468),
and `child_hashes` stores `child[1..]` of the child's `word_rlp` (`branch.rs:172-177`); `hashes` are
in nibble order, as the stack is. So with `hash_mask == state_mask` the stack of `[n]` in the serial
walk is `word_rlp(hash_i)` for every set bit, the same input `child_node` feeds `BranchNodeRef`.
The stored `BranchNodeCompact` for `[n]` depends only on masks at index 1, which only its children
set (`hash_builder/mod.rs:428-455`), so it is identical in both walks and in the union.
Every other shape returns `None` and the calling thread runs the one-thread walk
(`parallel.rs:396-411`): an empty nibble (`root == EMPTY_ROOT_HASH`, skipped, 304), a single leaf or
an extension at `[n]` (no update at `[n]`, `child_node` gets `None`, 343), a leaf or extension child
of `[n]` (`hash_mask != state_mask`, 344), fewer than two non-empty nibbles (318-321: the serial root
would be a leaf or extension, not a branch), and a stored root node (`has_stored_root_node`,
`parallel.rs:476-478`, checked before the split, 357-361: a stored root carries a `root_hash` the
serial walker would use to skip, which the split does not reproduce). A nibble that collapses to a
leaf or an extension by the block's deletions has no update at `[n]` either (the hash builder only
records branches), so it falls back; its removed node `[n]` is in the subtrie's `removed_nodes` as
in the serial walk (`walker.rs:334-340`). A pre-block extension at `[n]` that becomes a branch by the
block's insertions composes (the new branch's update exists and all its children are branches) or
falls back (a leaf child); both correct.

*Union of trie updates.* `finalize` drops the empty path from both the updated and the removed sets
(`updates.rs:146-151`, `354-360`), so the serial walk records nothing above `[n]`; the sixteen
subtries' `account_nodes`, `removed_nodes` and `storage_tries` are disjoint by first nibble and
their union is the serial set (`account_split.rs:313-315`); `TrieUpdates` equality is set equality
(`HashMap`/`HashSet`), which every test asserts (`parallel.1 == serial.1`).

*Storage pieces.* Same construction (`storage_split.rs:353-374`, cursors 413-489), with two
differences handled explicitly: `is_storage_empty` is answered for the whole storage (480-484), so
reth's short circuit fires in every piece only when the whole storage is empty, and `compose`
refuses a `deleted` piece (386-389) so the walk computes it and writes the `deleted()` marker as the
serial walk does; and the pre-check `splittable` (147-162) demands no stored root node and all
sixteen first-nibble nodes stored with every child hashed, judged on the pre-block trie, so a piece
always has a node to start from, and a post-block collapse still falls back through `child_node`.
A piece whose nibble lost every slot walks it (its prefix set holds the deleted keys), returns
`EMPTY_ROOT_HASH` with the removed nodes, and the composed root drops that child, as the serial
root does (test `whole_nibble_emptied`, `storage_split_tests.rs:201-222`).

*Contract created and destroyed in one output.* Block k creates (in `runs`), block k+1 destroys
(`current` has `None` + wiped): no task, the hashed account cursor returns the tombstone, the walk
meets no leaf, `finalize` writes `deleted`; the parallel and serial paths read the same layers. Within
one block the bundle holds no account and the hashed state is a tombstone (pinned by
`test_execution_cache_matches_fresh_reads`, `trie_overlay.rs:549-552`). Covered by `random_block`
rolls 0 and 1 (`parallel_tests.rs:216-221`) over persisted multi-block outputs and by the seeded
deltas of `trie_overlay.rs:62-124` through `parallel_layered_root_for_test` (161-164).

### Q2. Fallbacks and the determinism of the decisions
Every fallback runs the serial code over the walk's own transaction and factories: `few_changes`
(`AccountWalk::splits`, `account_split.rs:116-125`, decided by `worth_splitting` on the prefix set
alone, 129-132), `shape` (`compose` → `None` → `StateRoot::...root_with_updates` on the calling
thread, `parallel.rs:396-411`; storage: `take` → `Some(None)` → the walk computes,
`storage_split.rs:332-339`, `trie.rs:313-337`), `stored_root_node` (`parallel.rs:357-361`;
`splittable`, `storage_split.rs:152-154`), `mismatch` (`checked`, `parallel.rs:742-769`, returns the
serial tuple). The decisions are functions of the block's prefix sets and the stored trie shape
(`splittable` and `has_stored_root_node` read the layered trie), never of thread count, timing or
pool size: the pool only chooses which thread computes a nibble or a piece (`Subtries::work`,
`account_split.rs:206-227`; `StorageSplits::work`, 275-299), and the calling thread claims every
piece and nibble before it walks (`parallel.rs:388-392`), so `take`'s "claim what is left" arm
(`storage_split.rs:309-314`) is unreachable in production (only tests call `take` before `work`).
The sample is by block number (`block_is_checked`, `parallel.rs:250-256`; the number is
`parent.number + 1`, `execution.rs:429-434`), so every node checks the same blocks
(`every_node_checks_the_same_blocks`, `parallel_tests.rs:387-402`).

The off switches (`parallel.rs:211-232`, `account_split.rs:94-112`, `storage_split.rs:107-125`) are
read once into `OnceLock`s. A node restarted with a switch set computes the serial root for every
block; its peers compute the parallel root. The two are equal exactly when the parallel code is
right, which is the claim the sampled check tests; if it is wrong, that node parts from its peers at
the next block the bug hits, as the README says (`README.md:96-101`, `parallel.rs:102-107`). The
sampled check does not prevent a fork; it cannot, because every node runs the same code and
publishes the same root, right or wrong: the 255 unchecked blocks between two samples carry the
parallel result on every node, the checked block the serial one (`parallel.rs:288-303`), and no
peer verifies a root ("no payload's root checks this one", `parallel.rs:83`). What it does is turn a
silent wrong root into an alertable metric within 256 blocks of the first occurrence of the shape
that triggers it, with no divergence among same-release nodes. One consequence the docs do not
state (T5-2 below): if the bug also produced wrong trie updates on an unchecked block, those nodes
persisted them on every node, and every later root, serial or not, is computed over them; switching
the parallel paths off restores agreement, not the root of the true state (a from-scratch rebuild,
e.g. snapshot import, then hard-fails at that chain).

### Q3. Cancellation and errors
A task that fails does not fail the block and does not leave a root unset: `StorageRootTasks::run`
catches a panic (`parallel.rs:664`, `catch_unwind(AssertUnwindSafe(task))`) and records a failed
`Result` as `Done(None)` (665-667); the walk's `storage_root` then returns `None` (727-732) and the
walk computes that root itself over its own transaction (`trie.rs:313-337`). A helper's failure
(`walk_helper`, `parallel.rs:510-513`) or a nibble's (`Subtries::work`, `account_split.rs:219-225`)
or a piece's (`StorageSplits::work`, `storage_split.rs:291-297`) is the same: `Done(None)`,
recomputed on the calling thread (`Subtries::finish`, `account_split.rs:259-262`) or left to the
walk (`take`, `storage_split.rs:332-335`). The recompute on the calling thread is not under
`catch_unwind` and its error propagates (`finish(...)?`, `parallel.rs:394`; `TaskError::into_provider`,
584-594): a database error on the walk's own transaction fails the block, as it should. A panic that
reaches the calling thread (a deterministic one in `compose`, or in the recompute) unwinds through
`in_place_scope`, which waits for the spawned jobs and re-raises (rayon's scope semantics), and the
build fails; the release profile unwinds (no `panic = "abort"` in `Cargo.toml`), so `catch_unwind`
works as written. So: a task error is per-node, logged once a block (`log_failures`, 689-699;
`TipMoved` at error level, else warn) and changes no result when the parallel code is right; it is
the one per-node difference the design admits (`parallel.rs:95-97`). It is not counted in a metric
(T5-1).

"A failed walk claims its unstarted tasks": `ClaimUnstartedOnExit` is created first inside the
scope (`parallel.rs:366`) and its `Drop` (707-711) runs on every exit, including `?` and a panic;
`claim_unstarted` (679-686) turns every `Pending` slot into `Claimed`, and `run` returns at once for
a non-`Pending` slot (656-660). The subtries and pieces need no claim because the calling thread's
`work` calls (388, 392) exhaust both claim indices before any early exit (the first `?` after them
is 394); the comment at 702-704 is accurate. The scope's end then waits only for queued jobs that
return immediately. Test `failed_walk_starts_no_task` (`parallel_tests.rs:355-381`) pins it on a
one-thread pool. No wait cycle exists: slot tasks and pieces wait on nothing; a subtrie walk waits
only on a `Running` slot (722-726) or a claimed piece (`storage_split.rs:318-323`), and a claimed
piece is being computed by a thread inside `work`, which never waits.

## Findings

### T5-1. Failed, panicked and tip-moved root tasks are logged but not counted
- **Severity (initial)**: Low
- **Category**: Error Handling (diagnostics)
- **Location**: `crates/tn-reth/src/env/output_overlay/parallel.rs:671-675` (`record_failure`),
  `689-699` (`log_failures`), `crates/tn-reth/src/metrics.rs:443-564` (the fallback counters)
- **Claim**: a storage-root task, walk helper, subtrie or piece that fails (database error, panic,
  `TipMoved`) is logged once a block and has no metric, so the one per-node difference the design
  admits (`parallel.rs:95-97`: its part goes to the serial computation on that node only) cannot be
  alerted on or correlated with a later `parallel_state_root_mismatches_total` increment; the
  fallback counters cover only the shape decisions (`AccountWalkFallback`, `StorageWalkFallback`).
- **Failure scenario**: a node's disk starts returning read errors on the tasks' transactions (or a

## Considered and rejected
- **Composition drops the root-level masks.** The serial root branch's `tree_mask`/`hash_mask`
  (index 0) are never stored: `finalize` excludes the empty path (`updates.rs:148`, `151`), and the
  `[n]` node's compact form uses index-1 masks only (`hash_builder/mod.rs:444-453`). Holds.
- **A `[n]` node with an inline (sub-32-byte) branch child would make `child_hashes` panic or
  `child_node` miscount.** alloy-trie sets the hash bit for every branch child and slices
  `child[1..]` (`branch.rs:176`), so an inline branch would already break reth's own updates; an
  account leaf is ≥ 70 bytes and a storage branch at depth ≤ 60 has ≥ 33-byte children, so no
  branch shallower than depth 62 is inline. Not reachable.
- **A pre-block extension at `[n]` (account trie, no pre-check) composed wrongly.** Traced above
  (Q1): the subtrie builds the post-block branch at `[n]` if one exists, and `hash_mask ==
  state_mask` decides; the old extension's stored node `[n,m]` is visited (not skippable, no
  `root_hash`) in both walks. Holds.
- **Removed nodes under `[n]` depend on the walker's `can_skip_current_node` state inherited from
  the previous nibble.** `consume_node` recomputes it for the pushed node (`walker.rs:332`) and
  the removal decision uses it and the node's position (336-340); the root subnode's state is the
  same in both walks after `set_nibble`. Holds.
- **`SubtrieCursor::seek` clamping could move a layered cursor backwards.** Seek keys from
  `next_unprocessed_key` are non-decreasing and `max(key, [n]) ≥ key`; `ForwardInMemoryCursor`
  and the DB cursors are only ever asked for keys at or after their position. Holds.
- **The hashed `SubtrieCursor::next` past the nibble keeps advancing the inner cursor.** It returns
  `None` and the node iterator stops asking (`try_next` breaks when the walker has no key,
  `node_iter.rs:253-255`); extra inner advances are harmless reads. Holds.
- **Prefix-set entry at the boundary.** Account keys are 64 nibbles; storage keys too; `all` sets are
  excluded from both splits (`worth_splitting`, `wants_split`). No entry can be shorter than one
  nibble. Holds.
- **`is_empty()` of an `all` prefix set drops wiped storages from the targets.** `PrefixSet::is_empty`
  is `!all && keys.is_empty()` (`prefix_set.rs:244-246`): wiped storages get a task with the `all`
  set, identical to the walk's. Holds.
- **Two threads take one account's storage root (double `take`), or a result is taken by no one.**
  Each account leaf is visited by exactly one subtrie (its first nibble) or the one-thread walk;
  `storage_root` turns a slot `Claimed` on first take (722, 727-732) and `take` turns pieces `Taken`
  (319). Untaken results are dropped with the scope. Holds.
- **Deadlock: the calling thread blocks on a Condvar inside `in_place_scope` while the pool is
  saturated.** It waits only on `Running` slots and claimed pieces/nibbles, each computed by a thread
  already inside its job and waiting on nothing; `Pending` slots are claimed, not awaited
  (`parallel.rs:734`); unclaimed nibbles cannot exist at `finish` (`debug_assert!(all_claimed)`,
  `account_split.rs:243`, after `work` at `parallel.rs:392`). Queued helper jobs behind batch
  validation only delay the scope's end. Holds (latency, not correctness).
- **`catch_unwind` is a no-op under `panic = "abort"`.** No profile sets it (`Cargo.toml`). Holds.
- **A task could see an older or newer snapshot than the walk.** Single writer, tasks open after the
  walk, the persist writes state and `LastFinalizedBlock` in one transaction (`execution.rs:582-590`);
  the marker heal at `epoch.rs:184` runs at startup before any block; the snapshot import
  (`snapshot.rs:1061`) runs on its own env. The tip check catches any commit that advances the
  marker; one that changed state without it is the documented residual (`parallel.rs:79`). Holds.
- **The storage-root hook could serve a resumed (`previous_state`) walk a precomputed root.** The
  resume arm (`trie.rs:214-272`) never consults the source; TN uses `root_with_updates`
  (`with_no_threshold`) so no resume occurs. Holds.
- **The sampled check compares the root only.** It compares the tuple (`parallel.rs:748`) and
  returns the serial tuple (768). Holds.
- **Shadow mode could reach production and panic.** `Shadow` and `shadow_from_env` are
  `cfg(any(test, feature = "test-utils"))` (`parallel.rs:176-177`, 237-245), and in `test-utils`
  builds it is off unless `TN_PARALLEL_STATE_ROOT_SHADOW=1` (243). Holds.
- **The thread count changes a result.** `rayon::current_num_threads().min(WALK_HELPERS)` (381)
  only sizes the helper set; a one-thread pool computes everything on the calling thread through the
  same split code (`failed_walk_starts_no_task` shows the claim path). Holds.
- **TN-0105's shared cursors leave a previous account's overlay in place.** `set_hashed_address`
  resets and re-derives the overlay for the new address at every layer (`in_memory.rs:385-394`,
  `post_state.rs:425-433`, TN's `cursors.rs`, `storage_cursor.rs:130-134`); the `trie_overlay`
  differential over several accounts with storage would fail otherwise. Holds.
- **TN-0141 changes the `StoragesTrie` key bytes.** `to_compact_array` equals `to_compact` at
  every length (upstream's test, `nibbles.rs:211-223`). Holds.
