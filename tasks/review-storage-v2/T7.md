### T7-1. A rotation crash can leave a data file without its `.conf`, which no heal removes: the next start refuses the datadir
- **Severity (initial)**: Low
- **Category**: State & Durability / Error Handling
- **Location**: `storage/nippy-jar/src/writer.rs:55-98` (`NippyJarWriter::new`: `create_or_open_files` at 65, `jar.freeze_config()` only afterwards at 71), `writer.rs:145-178` (`create_or_open_files` creates the data and offsets files first), `fs-util/src/lib.rs:317-357` (`atomic_write_file`: tmp write, tmp `fsync`, rename, directory `fsync`), `storage/db/src/static_file/mod.rs:33-38` (`iter_static_files` loads every extension-less file's `.conf` with `?`), `storage/provider/src/providers/static_file/manager.rs:247-249` (`build` → `initialize_index` → `iter_static_files`).
- **Claim**: When a jar is created (a rotation in `increment_block`, `writer.rs:874-876` of the provider writer, or genesis), the data and offsets files are created before the configuration is written, and the configuration's own `fsync` of its temp file makes the two earlier creations durable before the rename; a power loss between that `fsync` and the rename leaves `static_file_<seg>_<a>_<b>` (and `.off`) with no `.conf`, and every later start fails in `iter_static_files` (`NippyJar::load` → `FsPathError::open`) with no heal, until an operator deletes the stray files. TN-0131 fixed the neighbouring state (configuration durable, offsets empty); this one is its mirror and is not handled.
- **Failure scenario**: a persist crosses a file boundary (every 500,000 blocks per segment at TN's default); the segment thread runs `Self::open` → `create_jar` → `NippyJarWriter::new`: `File::create(data)`, `File::create(offsets)`, 9-byte header (unsynced), `atomic_write_file`: `File::create(x.tmp)`, write, `fsync(x.tmp)` (on ext4 this commits the journal transaction that also holds the two directory entries) → power loss → `rename` never lands. Next start: `StaticFileProvider::read_write` → `initialize_index` → `iter_static_files` sees `static_file_headers_500000_999999` (parsed, since the name has no extension) and returns `Failed to load static file jar` / open error for its `.conf`; `ProviderFactory::new` fails; `layout::settle` is never reached.
- **Key Question**: Can a data file exist durably without its `.conf` after a crash in `NippyJarWriter::new` for a new jar (yes by the order above), and does any startup path tolerate a listed data file whose `.conf` is missing (no: `iter_static_files` line 38 propagates the error)?
- **PoC test**: in `tn_crash_tests.rs` style: write headers 0..2 with 2 blocks per file; drop the provider; delete `static_file_headers_2_3.conf` only (leave the data and `.off` files, or an empty data file and a 9-byte `.off`, the state `create_or_open_files` leaves); `provider(dir, checksums, 2)` must build and `latest_writer(Headers)` must open and append block 2. At HEAD the build fails in `initialize_index`.
- **Proposed fix**: write the configuration before the files: in `NippyJarWriter::new`, when `jar.rows == 0` and either file is missing, call `jar.freeze_config()` first and then `create_or_open_files` (a crash after the configuration alone is TN-0131's healed state; a crash before it leaves only an orphan `.conf`, which no listing sees and the next creation overwrites). Rotation path only, no hot-path cost. Alternatively, `iter_static_files` could skip a data file without a `.conf` whose offsets file is at most the 9-byte header and whose data file is empty (a creation leftover), and keep refusing any other missing `.conf` (damage).
- **Relevant Files**: `storage/nippy-jar/src/writer.rs`, `storage/db/src/static_file/mod.rs`, `fs-util/src/lib.rs`, `storage/provider/src/providers/static_file/writer.rs` (`open`, `increment_block`), `storage/nippy-jar/src/consistency.rs` (`reset_files`, for the healed sibling).
- **Source**: T7

### T7-3. `gap_at` takes the index lock while holding a jar-cache shard lock, the reverse of `update_index`'s order
- **Severity (initial)**: Low
- **Category**: Concurrency
- **Location**: `storage/provider/src/providers/static_file/manager.rs:1678-1707` (`gap_at` takes `&StaticFileJarProvider`, a `dashmap` `Ref` = shard read lock, and calls `get_lowest_range_start` → `self.indexes.read()` at 1691 and 1695), callers at 2828-2832, 3010-3014 (`account_block_changeset`, `storage_changeset`, provider held) and 2531-2533 (`fetch_range_with_predicate`, provider held); `update_index` 1438 (`indexes.write()`) then 1557 (`map.insert`, non-growing path), 1564-1572 (`map.iter()` and `map.remove` on every path); `get_or_create_jar_provider` 1297-1313 (`entry().or_try_insert_with`, a shard write lock, outside the index lock); `find_static_file` 2444-2453 (index read held across `get_or_create_jar_provider`).
- **Claim**: Readers normally take the index lock first and a shard lock second (`get_segment_ranges_from_block` releases the index before the shard; `find_static_file` holds index-read across shard locks), and `update_index` takes index-write then shards; `gap_at` is the one place that holds a shard lock and then asks for the index lock. With parking_lot's fair `RwLock` (a pending writer blocks new readers, both in `indexes` and in `dashmap`'s shards), the cycle reader(shard S read → wants index read) / `update_index`(index write → wants shard S: `insert`/`remove` directly, or `iter()`'s read blocked behind a pending shard writer) / cache fill(pending shard S write, waiting for the reader) is a deadlock. TN-0101 moved the growing path's `insert` out of the lock but left `iter()`/`remove` and the non-growing `insert` inside it.
- **Failure scenario**: `gap_at` reaches its index read only when the provider's jar does not hold `number` (`!jar_blocks.contains(number)`, 1694, or a transaction below the jar's first, 1690), i.e. a jar missing between two others, which `check_contiguity` refuses at every start (1769, 1885), or a runtime deletion (`delete_segment_below_block`, not called on TN). So no production interleaving exists on an intact datadir; the inversion is latent.
- **Key Question**: Is there any reachable state on TN where `gap_at` evaluates `get_lowest_range_start` while a `StaticFileJarProvider` is held and a commit's `update_index` runs on another thread? (I found none; the ordering is still inverted.)
- **PoC test**: a three-thread test with a segment missing its middle jar and `check_contiguity` skipped: T1 holds the upper jar's provider and calls `account_block_changeset(gap_block)` while T2 blocks in `or_try_insert_with` for another key of the same shard (use the `before_cache_insert` hook to park T2 after its load) and T3 runs `latest_writer(..).commit()` (an `update_index`). Expect T1/T3 to finish; at HEAD they can wait on each other.
- **Proposed fix**: read the segment's lowest range before taking the provider: `let lowest = self.get_lowest_range_start(segment);` at the top of `account_block_changeset`, `storage_changeset` and `fetch_range_with_predicate` (or inside `gap_at` before the provider is dereferenced is not possible, so pass it in). One index read per call, which the callers already pay in `get_segment_ranges_from_block`.
- **Relevant Files**: `storage/provider/src/providers/static_file/manager.rs`, `storage/provider/src/providers/static_file/jar.rs` (`LoadedJarRef`), `storage/provider/src/providers/static_file/mod.rs:43-44`.
- **Source**: T7
