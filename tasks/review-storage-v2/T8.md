### T8-1. `db reset-execution` on a snapshot-restored datadir leaves a node that cannot start: the README promises a full rebuild, but only the restored epoch's consensus pack is on disk
- **Severity (initial)**: Medium
- **Category**: Upgrade path / Docs
- **Location**: `crates/tn-reth/README.md:893-922` (the reset moves `restored-state-floor` "so on
  a datadir once restored from a state pack the rebuild executes and compares every epoch, the
  restored one included"); `crates/telcoin-network-cli/src/db/reset_execution.rs:31-40` (moves
  the floor marker, refuses nothing else); `crates/telcoin-network-cli/src/db.rs:883-887`
  (`db load-state` imports one `consensus_data` pack, the closed epoch's);
  `crates/node/src/manager/node/run_epoch.rs:238-253` (epoch 0 entry: `open_epoch_pack` then
  `replay_missed_consensus`, no pack fetch before it; the only pack request is at line 371, after
  replay); `crates/storage/src/consensus.rs:637-700` (`new_epoch(filler, committee0)` opens a
  fresh, empty epoch-0 pack with `open_append`), `crates/storage/src/consensus.rs:1575-1596`
  (`consensus_header_by_number` returns the current pack's `Err` when no staging pack exists);
  `crates/storage/src/consensus_pack.rs:5135-5142` (`ConsensusNumberTooHigh` for a number the
  pack does not hold); `crates/state-sync/src/lib.rs:299-303` (`?` propagates it).
- **Claim**: After `db reset-execution --force` on a datadir bootstrapped with `db load-state`
  (which holds consensus packs only from the restored epoch R on, and records 0..=R), the next
  start enters epoch 0 from the genesis tip, `new_epoch` creates an empty epoch-0 pack,
  `get_missing_consensus(epoch 0)` reads `consensus_header_latest()` from the restored tip pack
  and then `consensus_header_by_number(1)` from the empty epoch-0 pack, which fails with
  `ConsensusNumberTooHigh`; the replay returns the error and the node exits. Nothing fetches
  epochs 0..R-1's packs from peers before that read (startup syncs epoch *records* only,
  `node.rs` `sync_epoch_records_to_tip`; pack requests happen per epoch after replay).
- **Failure scenario**: restore a node from a state pack at epoch R (`db load-state`), run it,
  then follow the README's "Rebuilding in the new layout" on it: stop, `db reset-execution
  --force`, start. Expected (README): rebuild from genesis in v2 comparing every epoch. Actual:
  the start fails at the epoch-0 replay with a storage error from the empty epoch-0 pack, every
  restart the same; the operator has to roll back by hand (move the `execution-reset-*` entries
  back) and gets no message saying why.
- **Key Question**: Does any startup or epoch-0 path fetch the missing epoch packs from peers
  before `replay_missed_consensus` reads header 1, or does the first start after a reset on a
  restored datadir fail as traced?
- **PoC test**: e2e or node IT: `db load-state` a 4-validator network's epoch-2 bundle into a
  fresh datadir (the `state_export_import.rs` harness), run `db reset-execution --force` on it,
  start the node and assert it exits before serving RPC with a message naming the missing epoch
  packs (today: assert it exits with `ConsensusNumberTooHigh`/a replay error).
- **Proposed fix**: `db reset-execution` refuses a datadir whose `consensus-db/epochs/` has no
  `epoch-0` pack (equivalently: one carrying `restored-state-floor`), naming that the rebuild
  needs the consensus output from genesis and that a restored node must `db load-state` into a
  fresh datadir instead; the README's "the restored one included" paragraph is replaced
  accordingly. Off the hot path (CLI + docs).
- **Relevant Files**: `crates/telcoin-network-cli/src/db/reset_execution.rs`,
  `crates/telcoin-network-cli/src/db.rs`, `crates/node/src/manager/node/run_epoch.rs`,

### T8-2. A rebuild's replay-closes clear the live epoch's `Votes` and `LastProposed`, the equivocation guards, while that epoch may still be open on the network
- **Severity (initial)**: Medium
- **Category**: State & Durability (consensus guard gap)
- **Location**: `crates/node/src/manager/node/run_epoch.rs:258-266` (replay-and-close arm:
  `close_epoch(None)`, `write_epoch_record`, then `clear_consensus_db_for_next_epoch()`
  unconditionally, returning `NewEpoch`); `crates/node/src/manager/node/close_epoch.rs:1089-1102`
  (`clear_consensus_db_for_next_epoch` clears `LastProposed` and `Votes` whole);
  `crates/node/src/manager/node/close_epoch.rs:703-760` and `1317-1334`
  (`clear_stale_epoch_tables`/`current_epoch_guard_row`: the *entry* path explicitly keeps
  `Votes`/`LastProposed` rows of the epoch in progress, "the rows a clear must never take from
  the epoch in progress"); `crates/consensus/primary/src/network/handler.rs:1366-1412` (the
  vote-once rule is the stored `VoteInfo` per author: no row, no refusal);
  `crates/tn-reth/README.md:908-920` (the reset path says the node "is out of the committee's
  work for the whole rebuild" but never says to keep it stopped until its epoch closes, unlike
  Rollback at 975-981 which states that rule for a fresh datadir).
- **Claim**: A validator that voted in epoch K, is stopped, has `db reset-execution` run, and is
  restarted re-enters epoch 0 and closes epochs 0..K-1 through the replay-and-close arm; the
  first of those closes wipes K's `Votes` and `LastProposed` rows. If K is still open on the
  network when the rebuild reaches it (a short chain, or a long epoch), the node rejoins K with
  no record of the votes it cast, so a second, different header from an author at a round the
  node already voted on passes the vote-store check (`read_vote_info` → `None`) and is signed;
  with `f` Byzantine double-voters, quorum intersection (two quorums of `2f+1` in `3f+1` share
  `f+1`) then needs exactly one lapsed honest voter, which this is.
- **Failure scenario**: 4 validators, 24h epochs, chain young enough to rebuild in minutes.
  Operator resets validator-4 in epoch K at round r and restarts it; rebuild reaches K in
  minutes; the node catches up and returns to `CvvActive` inside K; a Byzantine author re-sends
  a conflicting round-r' (r' ≤ r, within the gc window) header; the node votes again. Expected: a
  refusal (`AlreadyVoted`), as on any restart without a reset. Actual: a vote.
- **Key Question**: Is there any check between the reset and the node going live in K that
  refuses to start, or keeps K's guard rows, when the consensus DB holds `Votes`/`LastProposed`
  rows of an epoch later than the one a replay-close is clearing? (I found none: the entry path
  only protects rows of the *entered* epoch, which is 0 at the first entry after a reset.)
- **PoC test**: node IT on the `run_epoch` harness: write a `Votes` row and a `LastProposed`
  header of epoch 3 (`epoch_carrying_tables()` from close_epoch tests), then drive a replay-close
  of epoch 0 (the `replay_anchored_on_block1_stops_at_the_epoch_close` fixture with
  `epoch_boundary = 3`) through `run_epoch(Initial)`; assert both epoch-3 rows survive. Today
  they are gone.
- **Proposed fix**: smallest: on the two replay/drain closes (not the live boundary arm) skip
  `Votes` and `LastProposed` when `current_epoch_guard_row` finds a row of an epoch later than
  the one being closed (log it, as `clear_stale_epoch_tables` does), or make the clear per-epoch
  for those two tables (remove rows with `epoch <= closed`). Plus the README sentence under
  "In place": a validator stays stopped after the reset until the network has closed the epoch
  it voted in (the rule Rollback already states). Hot path: none (epoch close only).
- **Relevant Files**: `crates/node/src/manager/node/run_epoch.rs`,
  `crates/node/src/manager/node/close_epoch.rs`,
  `crates/consensus/primary/src/network/handler.rs`, `crates/consensus/primary/src/proposer.rs`,
  `crates/tn-reth/README.md`.
- **Source**: T8

## Considered and rejected
Question 1, every source of a stored record and every honest reason its `final_state` can differ:
- **Restored datadir (snapshot).** `check_stored_final_state` returns `Restored` when
  `local.number <= floor` (close_epoch.rs:1278-1286); the floor is read once at env open
  (`crates/tn-reth/src/env/mod.rs:218`, 401-402). Only the restored block B can be a closing
  block at or below the floor (nothing below it was executed), and `db load-state` bound record
  R's `final_state` to B (README 487-491), so the entry check at B (`epoch_start_header` = B,
  close_epoch.rs:586-592) and any close at B are skipped; every block above B is compared. A
  restored datadir from before the marker existed has no floor and compares record R with B,
  which load-state made equal. Holds; pinned by `replay_guard_skips_a_closing_block_this_node_restored`.
- **Epoch-0 placeholder.** `write_epoch_record` reuses an epoch-0 record only with a certificate
  (close_epoch.rs:420-431), so the dummy (uncertified, default `final_state`) is built over, not
  compared; `recover_previous_epoch_record` routes a dummy to the re-derive path
  (close_epoch.rs:569-572). Pinned by `replay_guard_builds_over_the_dummy_epoch0_record`.
- **Uncertified own record from a fork.** Compared like a certified one and stops the node with
  `certified = false` in the message (close_epoch.rs:1187-1201). Stopping is the documented
  decision (README 924-949: fresh datadir, keep the moved-aside store) and is right: the record
  attests a chain this execution does not reproduce, and the store keeps one record per epoch
  (`save_record` → `ConflictingRecord`, epoch_records.rs:2209-2226), so running on would hide the
  divergence. Not every honest node: only the one that forked.
- **Record written by another binary / codec.** A record that does not decode reads as `None`:
  the close path then builds the record and `save_record` compares digests through
  `fetch(...).map_err(unreadable)` (epoch_records.rs:2214-2219), which errors and stops the node;
  the entry path errors explicitly (close_epoch.rs:574-587). Both fail closed; pinned by
  `epoch_loop_stops_when_the_previous_record_cannot_be_read`. `v0.16.0-adiri` writes the same
  `final_state` (the closing-block pin, `build_epoch_record`), so records from the previous
  release compare correctly.
- **A record for an epoch the node never executed.** State sync never executes past the current
  epoch (run_epoch.rs:1162-1168 invariant, `handle_sync_output`); pack catch-up replays every
  epoch; only a restore skips execution, and that is the floor case. No other honest shape.
- **A closing output with no batches.** The engine executes an empty output as a block when it
  closes the epoch (`ConsensusOutput::close_epoch_for_last_batch`, types/src/primary/output.rs:
  273-282, "also works for empty outputs with no batches", consumed at tn-reth/src/payload.rs:132;
  the faucet fix's comment at faucet.rs:353-356 states the same rule), `recent_blocks` gets that
  block in the same watch write
  (`announce_executed_output`, execution.rs:642-652), so `parent_state` is the real closing block
  on every node. Holds.
- **The certified-record-arrives-early race.** A slow validator whose epoch K is closed by a
  peer's certificate leaves through `closed_by_record` (run_epoch.rs:545-557), drains leftover
  output, and if the drain reaches the boundary, `write_epoch_record` compares the stored peer
  record with the block it executed after `wait_for_consensus_execution` (`close_epoch`,
  run_epoch.rs:817-845, the wait at 838; called from `finish_epoch` at 703-709). Same pin,
  correct comparison. Holds.

Question 2, the block-1 anchor and the guard:
- `anchors_on_itself` (start_epoch.rs:150-158) only relaxes the parent-hash check of header 1;
  the replay still hands the boundary header to the close, and the close compares the executed
  closing block, not the header (pinned by `replay_anchored_on_block1_stops_at_the_epoch_close`).
  A `db reset-execution` rebuild enters epoch 0 from the genesis tip (`epoch_state_at_epoch_start
  _from_tip`, epoch.rs:350-355), `recover_previous_epoch_record(0)` returns early, each
  replay-close compares the stored (certified) record with the re-executed closing block, and the
  next entry compares it again against `getEpochInfo(N).blockHeight - 1` (epoch.rs:356-372,
  `blockHeight == closing block + 1`, tripwired at 393-406). Both pins are the same block.
  `new_epoch` re-opens sealed packs for append (`Inner::open_append`, consensus_pack.rs:4060ff,
  retires the sentinel) and seals the tip pack at the first handoff (consensus.rs:709-717), so
  `consensus_header_latest()` reads it as static. Pre-existing restart-replay machinery; the
  resync e2e drives it across many boundaries.

Question 3, persistence order and durability at the close:
- The diff changes nothing the node persists before it acknowledges: run_epoch.rs's functional
  delta is the `epoch_start_header` argument (238) and test harness; start_epoch.rs passes the
  epoch (142-147). Order is unchanged: closing output persisted in the consensus pack before
  execution (`save_consensus_output` → `persist_current`), execution commit (`persist_blocks`,
  execution.rs:579-599, one transaction with finalized/safe markers) before the `recent_blocks`
  watch write (`announce_executed_output`, 642-652), the epoch record saved and
  `epochs().persist()` before it is published (close_epoch.rs:525-531), tables clear last.
- Execution-DB durability: the default `TnLmdbArgs` is `SyncMode::Durable`
  (tn-lmdb-reth/src/env.rs:201) and `tn_lmdb_args` keeps it unless `--db.sync-mode` is given
  (database.rs:761-779); nobody calls `TnLmdbEnv::sync` at the epoch close (grep: only the
  migration and tests). Under `safe-no-sync` there is a ≤1 s / 64 MiB window (database.rs:790-800)
  where record N is durable and the closing block's commit is not. A crash there re-enters epoch
  N from the older tip, replays the closing output from the durable pack, re-executes it
  deterministically, and the guard compares the stored record with the identical block. The
  acknowledged record is backed by re-derivable data, not lost. Not a finding (the weak-head
  open's correctness is another track's).
- `store_failure`/`ensure_stores_durable` (run_epoch.rs:1184-1198, 1237-1246) are unchanged.

Question 4, the bounded `get_missing_consensus`:
- The bound is "this epoch's headers plus the first header of another epoch" (lib.rs:299-307,
  `break`); past it nothing is read, there is no retry and no wait. The caller refuses the
  foreign header (start_epoch.rs:141-150) exactly as before the bound, and it only ever sees one
  because the replay stops at the close before reaching it. Reads are local (`consensus_chain`),
  so no peer can starve it, and `consensus_header_latest()` costs one static-pack open per entry.
  A number absent inside the epoch (`Ok(None)`) is skipped and the replay's contiguity check then
  fails closed. The only way to "stall at the bound" is a datadir with no pack for the entered
  epoch, which is T8-1, not a bound issue. Pinned by `missing_consensus_stops_after_the_entered_epoch`
  (7 cases, headers compared to the stored prefix).
