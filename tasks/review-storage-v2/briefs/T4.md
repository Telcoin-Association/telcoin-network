The execution cache is a cross-block cache of state reads under block building (the branch's
own description: "wiped-account set, sampled hit checks, pin"). Questions:
1. Correctness of the cache against the database: what is cached (accounts, storage, bytecode,
   block hashes?), keyed by what, and invalidated by what. For each write that can change a
   cached value (a block's bundle state applied to the overlay, a persist, a wiped account
   (SELFDESTRUCT / account removal), a storage slot zeroed, an epoch close's system calls,
   a snapshot restore, `db reset-execution`, a restart), prove the next read sees the new
   value. The "wiped-account set": does a wipe clear every storage slot of the account in the
   cache, including slots read before the wipe in the same block and slots never read?
   What about a recreated account (CREATE2 at a wiped address in the same output)?
2. Determinism: can two validators executing the same output ever read different values because
   one had a cache hit and the other a miss (a stale hit = divergence = Critical)? The "sampled
   hit checks": what is sampled, by what key (block number, so every node samples the same?),
   what happens on a mismatch (log, metric, which value is used, does the node stop?). Is the
   cache ever consulted for RPC `eth_call`/trace reads or only block building? Is it shared
   between the block builder and the RPC thread (a race)?
3. The "pin": what is pinned, for how long, and what unpins it on an error path (a failed block,
   a panic caught by the engine, an epoch boundary). Memory bound: what caps the cache
   (entries, bytes), and can a crafted workload (many distinct slots) grow it without bound?
4. `execution.rs` and `payload_builder.rs` deltas: the persist still writes the blocks and the
   finalized/safe markers in one transaction; signer recovery off-thread (main's #1827 merged
   here: did the merge keep both sides' invariants?); the `InvalidTx` skip rule; the
   unrecoverable-signer drop. `evm/block.rs` and `epoch.rs`: any change to what a block's
   system calls read or write.
5. TN-0082 (a missing bytecode row fails the lookup) in `vendor/reth/crates/revm/src/database.rs`:
   confirm the error propagates to the block build as a failure and not as a skipped transaction,
   and that the exec cache cannot serve an empty code for the same key.
6. `txn_pool.rs`: the maintenance task's reorg handling and anything that changed in how the
   worker pool admits or evicts (the pool backports TN-0041..0043, TN-0073..0075 are T6's; here
   only TN's own side).
