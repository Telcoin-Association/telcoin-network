## Findings

### T6-1. `--rpc.max-active-filters` bounds the number of installed filters, not their size
- **Severity (initial)**: Medium
- **Category**: Security (DoS)
- **Location**: `vendor/reth/crates/rpc/rpc/src/eth/filter.rs:625-637` (`install_filter`),
  `:350-355` (`eth_newFilter` stores the whole `Filter`), `vendor/reth/crates/rpc/rpc-server-types/src/constants.rs:22`
  (`DEFAULT_MAX_ACTIVE_FILTERS = 1000`), `crates/tn-reth/src/rpc_server_args.rs:157-159`
  (15 MB request body), `vendor/reth/CHANGES.md` TN-0056 *Why* ("each one can carry a filter
  near the request size limit").
- **Claim**: TN-0056 (the fix for review R2) caps installed filters at 1,000 node-wide but stores
  each `eth_newFilter`'s `Filter` (`FilterSet<Address>` and four `FilterSet<B256>` hash sets,
  alloy-rpc-types-eth 1.8.3 `filter.rs:22, 403`) unbounded, so one unauthenticated `eth` client
  can pin about 1,000 x 15 MB of filter sets for as long as it polls each filter once per five
  minutes.
- **Failure scenario**: a client on the default `eth` namespace sends 1,000 `eth_newFilter`
  requests, each a 15 MB body of ~340k distinct `address` entries (parsed into a `HashSet`,
  ~15 MB resident each); every 4 minutes it sends 10 batches of 100 `eth_getFilterChanges`
  (the batch limit) to keep them fresh (`filter_changes` updates `last_poll_timestamp`,
  `filter.rs:260`). The node holds ~15 GB of filter state indefinitely; the 1,001st
  `eth_newFilter` from any other client is refused with -32604, so the cap is also a cheap
  denial of filters to honest clients. Connection limits do not help: filters outlive the
  connection (`filter.rs:179-181` doc).
- **Key Question**: is a 15 MB `Filter` really retained in full by `install_filter` (no
  normalisation, no size check between parse and `filters.insert`)?
- **PoC test**: in `filter.rs` tests, build an `EthFilter` with `max_active_filters: 2`, install
  one `Filter` whose `address` set has 1,000,000 entries, and assert `install_filter` accepts it
  and the process RSS or `std::mem::size_of_val`-style estimate grew by the set's size; then
  assert a 101-address filter is accepted while a filter above a proposed per-filter cap is
  refused.
- **Proposed fix**: refuse a filter whose `address.len()` or any `topics[i].len()` exceeds a
  small cap (geth refuses nothing but has no persistent filters of this size either; 1,000
  addresses and 1,000 topics per position would serve every real client) in `install_filter`
  and in `logs_for_filter`, with a flag `--rpc.max-filter-entries`; or bound the sum of entries
  across installed filters. Hot path: `eth_newFilter` and `eth_getLogs` admission only.
- **Relevant Files**: `vendor/reth/crates/rpc/rpc/src/eth/filter.rs`,
  `vendor/reth/crates/rpc/rpc-eth-types/src/builder/config.rs`,
  `vendor/reth/crates/node/core/src/args/rpc_server.rs`, `vendor/reth/CHANGES.md` (TN-0056).
- **Source**: T6

### T6-2. `eth_subscribe("logs")` filters are outside the filter cap; bounded only by subscriptions x connections
- **Severity (initial)**: Low
- **Category**: Security (DoS)
- **Location**: `vendor/reth/crates/rpc/rpc/src/eth/pubsub.rs:109-119` (the `Filter` moves
  into `log_stream`, `:409-425`), `:241-243` (one task per subscription),
  `crates/tn-reth/src/rpc_server_args.rs:165-167` (1,024 subscriptions per connection),
  `:185-187` (500 connections).
- **Claim**: a `logs` subscription holds its client-supplied `Filter` for the life of the
  connection and is not counted by `--rpc.max-active-filters` (TN-0056 covers
  `eth_new*Filter` and the pool listeners only), so on a node with `--ws` the bound on
  retained filter bytes is `max_subscriptions_per_connection x max_connections x request size`
  (1,024 x 500 x 15 MB), which is no bound in practice.
- **Failure scenario**: one WebSocket client opens 1,024 `eth_subscribe("logs", <15 MB
  filter>)` subscriptions on one connection and keeps the socket open: ~15 GB resident and
  1,024 tasks each walking every committed block's receipts against a 340k-entry set
  (`logs_utils::matching_block_logs_with_tx_hashes`, `pubsub.rs:416-421`). `ws` is off by
  default and binds localhost, so this needs an operator who exposes WebSocket.
- **Key Question**: does any per-connection or per-node bound other than the subscription and
  connection counts apply to a `logs` subscription's `Filter`?
- **PoC test**: with `rpc_max_subscriptions_per_connection = 2` and `max_active_filters = 1`,
  open two `logs` subscriptions with large filters on one WS connection: both are accepted
  (the filter cap does not apply), the third is refused by jsonrpsee's subscription limit.
- **Proposed fix**: the same per-filter entry cap as T6-1 applied in `handle_accepted` for
  `SubscriptionKind::Logs` (`pubsub.rs:111-117`); optionally count live `logs` subscriptions
  against `max_active_filters`. Hot path: subscription setup only.
- **Relevant Files**: `vendor/reth/crates/rpc/rpc/src/eth/pubsub.rs`,
  `vendor/reth/crates/rpc/rpc/src/eth/filter.rs`.
- **Source**: T6

### T6-3. `eth_simulateV1` is outside the per-request gas budget: up to `max_simulate_blocks` x the block gas limit per request
- **Severity (initial)**: Low
- **Category**: Security (DoS)
- **Location**: `vendor/reth/crates/rpc/rpc-eth-api/src/helpers/call.rs:75-77` (256-block
  cap), `:164-170` (a block gas-limit override is refused only above both the block limit and
  the call cap), `:182-213` (per-block gas is `block_gas_limit`, calls without `gas` split it),
  `:92-95, 104-105` (one blocking-IO permit for the whole request); `crates/tn-reth/src/rpc_call.rs:320-345`
  (TN's wrapper adds the proof-permit hold only); `vendor/reth/crates/rpc/rpc-eth-types/src/call_many.rs`
  (TN-0057's budget, not applied here).
- **Claim**: TN-0057 bounds `eth_callMany`, `trace_callMany` and `debug_traceCallMany` to
  2,380 calls and 50M gas used per request, but `eth_simulateV1`, in the same default `eth`
  namespace and on the same blocking-IO permit, may run 256 simulated blocks of up to 50M gas
  each (12.8e9 gas, about 250x the callMany budget) with cancellation only between calls.
- **Failure scenario**: an unauthenticated client sends `eth_simulateV1` with 256
  `blockStateCalls`, each one call to a loop contract with `gas: 50_000_000` and
  `blockOverrides.gasLimit: 50_000_000` (`:165-168` accepts it, equal to the call cap). One
  request occupies a `tn-rpc-blocking` thread for minutes; 256 such requests (the blocking-IO
  permit count) occupy the whole RPC pool, and 25 of them hold the proof-permit guard TN's
  wrapper takes (`rpc_call.rs:327`), so `eth_getProof` and other simulations queue behind them
  until the clients disconnect (cancellation then stops them at the next call,
  `simulate.rs:236-238`).
- **Key Question**: can a client raise a simulated block's gas limit to the call cap through
  `blockOverrides.gasLimit`, and is the per-block budget really independent of the request's
  block count?
- **PoC test**: extend `call_many_budget_tests` (`rpc/src/eth/helpers/call.rs`): a
  `simulate_v1` payload of three blocks whose single calls each use 30M gas under a 50M cap
  succeeds today (90M used); assert it is refused once a request budget is applied.
- **Proposed fix**: charge each simulated block's `gas_used` against one `CallManyBudget::new(call_gas_limit)`
  (or `max_simulate_blocks x block gas limit` as an explicit, documented budget) in
  `simulate_v1`'s loop after `execute_transactions`; alternatively a lower
  `--rpc.max-simulate-blocks` default on public nodes. Hot path: `eth_simulateV1` only.
- **Relevant Files**: `vendor/reth/crates/rpc/rpc-eth-api/src/helpers/call.rs`,
  `vendor/reth/crates/rpc/rpc-eth-types/src/simulate.rs`, `crates/tn-reth/src/rpc_call.rs`,
  `docs/src/rpc-methods/eth/README.md`.
- **Source**: T6

### T6-6. TN-0079 counts opcode steps only: the call-trace arena copies every call's calldata uncounted, so R4's bomb still works through every `TracingInspector` tracer
- **Severity (initial)**: Medium (High on a node that serves `debug`/`trace` to untrusted
  clients; both are opt-in and documented private-only)
- **Category**: Security (DoS)
- **Location**: `patches/revm-inspectors/src/tracing/mod.rs:706-745` (`Inspector::call`),
  `:732` (`inputs.input_data(context)`, a `Bytes::copy_from_slice` of the shared memory range,
  `:837-845`), `:456` (`trace.output = output.clone()` on call end), `:177-199` (`record_bytes`,
  reached only from `start_step`, `:542-558`); `vendor/reth/CHANGES.md:1369-1370` ("Call,
  prestate and 4byte tracers record no steps and are unaffected").
- **Claim**: `TracingInspector` records a `CallTrace` with a fresh copy of the calldata for
  every CALL/STATICCALL/DELEGATECALL/CREATE regardless of config, and nothing counts those
  bytes against `max_recorded_bytes`, so a cheap call loop under the 50M gas cap allocates
  gigabytes through `callTracer`, `prestateTracer`, `flatCallTracer`, the struct logger and
  every `trace_*` method, and the 160 MiB cap of TN-0079 never trips.
- **Failure scenario**: a contract expands memory to 16 KiB once, then loops
  `STATICCALL(gas=0, <EOA>, 0, 16 KiB, 0, 0); POP; JUMP` (~144 gas per call). Measured in the
  patched crate with `max_recorded_bytes = Some(1)`: at 300,000 gas, 2,080 call traces holding
  34,062,336 bytes of copied calldata, `recorded_bytes() == 0`, no error, for the callTracer
  preset and for `default_parity()`; the struct logger counted 5.9 MB of its 34 MB. At the
  50M call gas cap that is ~5.5 GB per `debug_traceCall`/`trace_call` (~21 GB with 64 KiB
  arguments), allocated before the response-size limit applies; a mined 30M-gas transaction of
  this shape makes every `debug_traceTransaction`, `trace_transaction`, `trace_replayTransaction`,
  `trace_block` and `trace_filter` of it the same allocation. The node is OOM-killed by one
  request on any node that exposes `debug` or `trace`.
- **Key Question**: is there any path in `start_trace_on_call`/`fill_trace_on_call_end` that
  charges the input or output copy against the shared counter?
- **PoC test**: `tasks/review-storage-v2/T6-poc-call-arena.rs` (append to
  `patches/revm-inspectors/src/tracing/mod.rs`, `cargo test --lib review_poc`; three tests,
  all pass on HEAD, each asserting the arena holds tens of MB with the cap at 1 byte and no
  error).
- **Proposed fix**: in `start_trace_on_call` count `input.len() + size_of::<CallTraceNode>()`
  and in `fill_trace_on_call_end` `output.len()` against `recorded_bytes`; on overflow set the
  context error as `record_bytes` does and return `Some(CallOutcome)` with
  `InstructionResult::FatalExternalError` from `call`/`create` (the shape
  `vendor/reth/crates/rpc/rpc/src/js_tracer_interrupt.rs:191-217` uses, since the call hook
  has no `Interpreter` to `halt_fatal`). Logs are gas-bounded (8 gas/byte) and can be left
  uncounted. Re-port with PATCH.md's cap section. Hot path: tracing only; block execution runs
  no inspector from this crate.
- **Relevant Files**: `patches/revm-inspectors/src/tracing/mod.rs`,
  `patches/revm-inspectors/src/tracing/config.rs`, `patches/revm-inspectors/PATCH.md`,
  `vendor/reth/CHANGES.md` (TN-0079).
- **Source**: T6 (revm-inspectors slice; PoC and the `call` hook verified by hand)
