## Findings

### T1-1. `GapFill::Auto`'s width is never clamped to `CANDIDATES`/`MAX_GAP_FILL` on the fill path; `cheapest` returns `u32::MAX` when every prediction is NaN
- **Severity (initial)**: Low
- **Category**: Error Handling (defensive bound on a hot-path input)
- **Location**: `crates/tn-lmdb/src/env/gap_auto.rs:514-524` (`cheapest` falls back to `(u32::MAX, INFINITY)`), `:341` (`self.take(cheapest(...).0)`), `:369-374` (`take` stores any width), `crates/tn-lmdb/src/env.rs:1101-1108` (`width` from `choice.width` goes straight to `fill_gaps`), `:1210-1221` (`clean > width` is the only bound; `gap_buf.resize(clean * size)`)
- **Claim**: The only enforcement of `MAX_GAP_FILL` on the auto path is the invariant that `AutoGap::choice` is always a member of `CANDIDATES`; `Env::open`'s check (`env.rs:1864-1868`) and `FromStr` (`:193`) bound only `GapFill::Pages`. `fill_gaps` takes any `u32` and will read-and-rewrite every gap up to that width, growing `gap_buf` to `clean * page_size` bytes. If `cheapest` ever sees all-NaN costs (every candidate's `predict` NaN) it returns width `u32::MAX`, `take` adopts it, and the next scattered step rewrites every gap of the file whatever its width (a gap of a million clean pages = a 4 GiB bounce buffer).
- **Failure scenario**: NaN needs `correction(at) * sync` with `correction == 0` (every held step's `s.ns == 0`) and `sync == +inf` (a fit whose coefficients overflowed in `predict`). I could not construct it from real timings (`lap` of an fdatasync is never 0 ns; `solve_on` returns only finite coefficients), so this is a latent, practically unreachable path, not a live bug. No byte changes even then (the rewrite stores the page's own bytes), but memory and I/O are unbounded by the option's documented maximum.
- **Key Question**: Is "the choice is always a candidate" meant to be a type-level invariant? If so, make it one (clamp or assert at `take`, and `width.min(MAX_GAP_FILL)` in `make_durable`) rather than a `debug_assert` in `slot` that only fires on the next `observe`.
- **PoC test**: unit test on `AutoGap`: force `model.fixed = f64::INFINITY` and a held sample with `ns = 0.0`, call `choose` after the warm-up, assert `choice.width <= MAX_GAP_FILL`. Today it returns `u32::MAX` (and `slot(u32::MAX)` panics in debug on the following `observe`).
- **Proposed fix**: In `AutoGap::take`, `debug_assert!(CANDIDATES.contains(&width))` and `self.choice = if CANDIDATES.contains(&width) { width } else { 0 }`; in `make_durable` (`env.rs:1101`) `let width = width.min(MAX_GAP_FILL);`. Cold path (once per durable step), no hot-path cost.
- **Relevant Files**: `crates/tn-lmdb/src/env/gap_auto.rs`, `crates/tn-lmdb/src/env.rs`
- **Source**: T1

### T1-2. The weak-head check's read-ahead advises a damaged overflow cell's full `len` (up to 4 GiB) before the walk refuses it
- **Severity (initial)**: Low
- **Category**: Security (input validation, cost only)
- **Location**: `crates/tn-lmdb/src/check.rs:538-542` (`run_pages(ovf.len as usize, page_size)` with no `MAX_VALUE` or in-file check), `:551-556` (`ahead.add(pgno, pages)` gated only by `descends(txn)`), `:209-223` (`Ahead::start` → `sys::will_need` of the merged range), `crates/tn-lmdb/src/overflow.rs:178-192` (the walk's `checked_run` refuses `len > MAX_VALUE` and a run past `page_count` before any read)
- **Claim**: `read_ahead_of_leaf` advises `POSIX_FADV_WILLNEED` for `run_pages(ovf.len)` pages from `ovf.pgno` for every overflow cell whose txn is after the last sync, using the cell's bytes unchecked, whereas the walk that follows (`claim_run` → `checked_run`) refuses a cell with `len > MAX_VALUE` (16 MiB) or a range past the page count before touching a page. A cell damaged at rest to `len = u32::MAX` therefore starts a kernel readahead of up to 4 GiB of the file (clamped to the file size by `force_page_cache_ra`), synchronously allocating and submitting the reads, then the check falls back to the last sync. On a cold cache after an unclean end this is the exact situation the read-ahead exists for.
- **Failure scenario**: NoSync writer with a table holding an overflow run; process crash; one bit flipped in the cell's `len` high byte on the device (a torn sector of the leaf would fail the CRC first, so this needs damage inside a page the CRC still covers — the walk's CRC check runs on the leaf before `read_ahead_of_leaf`, so in practice the leaf's CRC refuses the page first). Residual: a leaf whose CRC was restamped by a tool, or a len inside a page whose CRC matches by chance (2^-32). Cost only; the open still falls back correctly.
- **Key Question**: Does the walk's CRC check on the leaf (`check.rs:320-322`) always precede `read_ahead_of_leaf` (`:336-338`)? Yes: so this is reachable only by damage under a valid CRC. Verifier should confirm there is no path where `read_ahead_of_leaf` runs on an unverified leaf.
- **PoC test**: build a file with an overflow run, restamp a leaf cell's `len` to `u32::MAX` (`crc::add_crc32_nonzero` as `damage_runs.rs` does), crash and reopen; assert `sys::take_will_need_log()` contains no range longer than `run_pages(MAX_VALUE)` pages. Today it contains one of ~1M pages.
- **Proposed fix**: In `read_ahead_of_leaf`, skip the cell when `ovf.len as usize > MAX_VALUE` or `ovf.pgno < 2 || ovf.pgno.checked_add(pages).is_none_or(|end| end > page_count)`. Cold path (open after an unclean end only).
- **Relevant Files**: `crates/tn-lmdb/src/check.rs`, `crates/tn-lmdb/src/overflow.rs`, `crates/tn-lmdb/src/sys.rs`
- **Source**: T1

### T1-3. `BootFile::write`'s error wrapper drops the OS error code that `PORTING.md` says callers walk sources for
- **Severity (initial)**: Low
- **Category**: Error Handling (diagnostics)
- **Location**: `crates/tn-lmdb/src/boot_record.rs:303-305` (`named = |e| io::Error::new(e.kind(), format!(...))`), `:320-331` (every error of `write` goes through it, the `fsync_file` one included), `crates/tn-lmdb/src/sys.rs:145-175` (`Context`, the crate's pattern that keeps the source and its `raw_os_error`), `crates/tn-lmdb/PORTING.md` "Errors" (sources are walked for the OS code "as the reth adapter does")
- **Claim**: `mark_open` (`env.rs:1425-1448`) fails `Env::open` with the boot record's error for anything but a refused create; that error is rebuilt as `io::Error::new(kind, String)`, so `raw_os_error()` is `None` and `source()` is `None`. An `EIO` from the record's `fsync` at open, or an `ENOSPC` from its write, reaches the adapter and the node as "the boot record <path>: ..." text with no errno, unlike every `sys.rs` error, which keeps it through `Context`. The `kind` is kept, so `mark_open`'s `PermissionDenied | ReadOnlyFilesystem` match still works.
- **Failure scenario**: Operator sees "open failed: the boot record /data/db.boot: input/output error" without the code the adapter's error mapping and the node's logs key on. No wrong behaviour; a fail-closed open with weaker diagnostics.
- **Key Question**: Does any caller (tn-lmdb-reth's error mapping) depend on `raw_os_error` of an `Error::Io` from `Env::open`? If so this is a regression for one new error source; if not, Informational.
- **PoC test**: `boot_record::tests`: write to a FIFO/dir path, or chmod the record 0444 and `write(.., false, true)`; assert `e.raw_os_error().is_some()` or that `std::error::Error::source(&e)` downcasts to an `io::Error` with `Some(libc::EACCES)`, as `sys::tests::a_failed_directory_sync_keeps_the_original_error` asserts for directories.
- **Proposed fix**: Reuse `sys::Context::wrap(format!("the boot record {}", path.display()), e)` (make `Context` `pub(crate)`) in place of `named`. No hot path.
- **Relevant Files**: `crates/tn-lmdb/src/boot_record.rs`, `crates/tn-lmdb/src/sys.rs`, `crates/tn-lmdb-reth/src/lib.rs` (error mapping)
- **Source**: T1

## Considered and rejected

Each item is a suspect I traced; the lines show why it holds.

**Q1 Gap fill (byte identity, bounds, concurrency, crash).**
- *Source of the bytes*: `fill_gaps` reads each gap through the file (`PageFile::read_resident` → Linux `preadv2(RWF_NOWAIT)` `file.rs:566-581`, macOS `read_exact_at` `:587-591`) into the writer's private `gap_buf` (`env.rs:1219-1224`) and writes the same buffer back at the same offset with `pwrite` (`PageFile::rewrite` `file.rs:598-604`). Never through the mapping, so no `&mut` into a page a reader may slice. The kernel's `pread` returns the page-cache page (dirty or clean), and `pwrite` stores into that same page-cache page, so readers of the mapping (`MapView::slice`, `file.rs:166-184`) see each byte take its own value.
- *Nothing changes a gap page between read and write*: the writer state is exclusive (`EnvInner::take_writer` `env.rs:601-612`; `Env::sync` waits in `with_writer` `:2069`; the close needs the writer home `:664`); the fill runs inside `make_durable` on the writer's thread (`:1104-1108`) with no allocation, remap (`grow` needs `&mut PageFile` via `alloc`, `:1602`) or trim (`trim_tail` only in `EnvInner::drop`, `:671`) possible meanwhile. Readers never write.
- *Gap pages are never a meta, past the published length, or in the trimmed tail*: every page of `pages` is a stamped private page or an `unsynced` one (`stamp_private` `alloc.rs:519-530`, `take_unsynced` `env.rs:1038-1047`), allocated by `Allocator::allocate` from the pool (free-list pages, which `decode_pages` refuses below 2 or at/above `page_count`: `freelist.rs:163-167`) or from the end (`< alloc.page_count()`); gaps are strictly between two of them (`w[0]+1 ..= w[1]-1`, `env.rs:1210-1218`), so every gap page is in `2..page_count` and below the file length; `check_inside` (`file.rs:607-615`) refuses any range past `self.len` as a belt. Pages are distinct and ascending (PageSet drain; `debug_assert` `:1040-1044`).
- *Bytes a gap page may hold*: a page of a slot's or reader's state (never written by anyone), a free page, a page this txn took and gave back (dirty with `alloc`'s one-byte store `env.rs:1611` or a layout; rewriting its cached bytes changes nothing), an aborted txn's or dead writer's page (same). All keep their bytes.
- *Crash mid-fill*: the gap's bytes are unchanged whether or not a sector was rewritten; M's dirty pages are written whole by step 4's sync, which has not run yet, so the crash recovers L exactly as a crash after step 3 does (crash matrix with gap fill on: `tests/crash.rs:398-408`, `:433-442`, `tests/crash_runs.rs:218-227`).
- *Filled gaps lie inside what step 4 syncs*: `MAX_GAP_FILL <= MERGE_GAP` const-asserted (`env.rs:133`); fixed width ≤ 64 at open (`:1865`), auto ≤ 64 by `CANDIDATES` (`gap_auto.rs:79-81`, see T1-1 for the missing clamp); `DataSync::Range` covers first..last, `File` the file, macOS `Ranges` each merged range (`merged_ranges` `:1836-1841`).
- *Failed writeback re-dirtied by a fill*: a page a failed writeback left clean is only possible after the environment latched (the error is reported to this writer's sync), and a latched writer never commits again (`RwTxn::commit` `txn.rs:3083`). Not reachable.
- *Partial `pwrite`*: `write_all_at` loops; any error poisons the file and fails the commit (`file.rs:602`, README "Errors" matches).

A nested root decoded for the read-ahead uses `nested_tag(tag, k)` (`:544`), the same the walk uses (`:470`).
