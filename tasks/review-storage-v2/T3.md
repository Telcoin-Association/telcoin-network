### T3-1. The migration does not detect a process that holds the MDBX database open, and `finish` unlinks `mdbx.dat` from under it
- **Severity (initial)**: Low
- **Category**: Concurrency / Upgrade path
- **Location**: `crates/tn-reth/src/env/database/migrate.rs:557-572` (`open_mdbx_read_only`,
  non-exclusive), `:737-742` (the commit-point check is the last transaction id plus a stat),
  `:965-978` (`finish` compares a stat, then removes `mdbx.lck` and `mdbx.dat`)
- **Claim**: the source record (`MdbxSource`: last txnid, length, mtime) detects writes made
  before the commit point or before `finish`, but not an MDBX environment another process holds
  open without having committed yet; the migration then removes `mdbx.dat` and `mdbx.lck` while
  that process has them mapped, and every commit that process makes afterwards goes to an
  unlinked inode and is lost when it exits.
- **Failure scenario**: the README's own threat model, two datadirs naming one `db/`: a
  `v0.16.0-adiri` node (reth on MDBX, no directory flock, no backend guard) has `db/` open and is
  idle (it opened before the migration started, or in the window between the rename and the
  version file). The tn-lmdb node starts: the copy's txnid and stat match at the commit point
  (no commit happened), the record matches at `finish`, `mdbx.dat` and `mdbx.lck` are unlinked.
  The old node keeps running on the unlinked file; its next commits are durable nowhere, and
  neither node reports anything. With the old node writing instead, the existing checks catch it
  (test `an_mdbx_commit_during_the_copy_fails_the_migration`, `mdbx_written_after_the_commit_point_is_refused`).
- **Key Question**: does libmdbx's `MDBX_EXCLUSIVE` on a read-only open return `MDBX_BUSY`
  when another process has the environment open (it does on Linux and macOS: the exclusive mode
  takes the whole-file lock), so that an exclusive read-only open of the source refuses a live
  holder before anything is copied?
- **PoC test**: in `migrate/tests.rs`, `build_mdbx(&path)`; open it RW through reth's
  `create_db`/`init_db` in a child process (the pattern of `mdbx_writer_process`) that opens, waits
  on a file flag, then commits one row and exits; run `open(&path)`: today the migration succeeds,
  `mdbx.dat` is gone, the child's commit returns `Ok`, and the row is nowhere (not in
  `tn-lmdb.dat`, and `mdbx.dat` no longer exists). Expected after the fix: the migration is
  refused with a "stop that process" error while the child holds the environment, MDBX untouched
  (`assert_untouched`).
- **Proposed fix**: open the source with `DatabaseArguments::default().with_exclusive(Some(true))`
  in `open_mdbx_read_only` (and map `MdbxError::Busy` to "another process holds the MDBX
  database: stop it, then start again", beside the existing `WANNA_RECOVERY` hint). The lock is
  held for the copy; `finish` on a later open cannot take it (MDBX closed), so the stat check
  stays as the finish-time guard. Touches only the migration (a one-time path).
- **Relevant Files**: `crates/tn-reth/src/env/database/migrate.rs`,
  `crates/tn-reth/src/env/database/migrate/tests.rs`,
  `vendor/reth/crates/storage/db/src/implementation/mdbx/mod.rs` (how `exclusive` reaches
  `EnvironmentFlags`), `crates/tn-reth/README.md` "Migrating from MDBX" (the refusal table)
- **Source**: T3

### T3-2. `migrate_from_mdbx` classifies the directory from stats taken before it takes the directory lock

  a state the directory no longer holds: `(true,false,false)` runs `migrate`, which removes the

  directory that is in fact migrated; `(true,true,false)` with `stopped_after_commit_point` now
  false returns `both_engines` ("resolve by hand: start from a fresh datadir") for a directory
  that is a finished, healthy migration. Both are transient (the next start opens normally), and
  no branch reached through stale flags removes or writes a data file, but the operator is told
  to discard a good datadir.
- **Failure scenario**: two datadirs name one `db/` (the setup the flock exists for). Node A is
  in `finish`; node B stats `(true,true,false)`, A finishes and drops the lock, B takes the lock,
  `stopped_after_commit_point` is false, B refuses with `both_engines`. The error text says the
  directory holds both engines' files; it holds `tn-lmdb.dat` and the marker only.
- **Key Question**: can the flags be re-read after `lock_db_dir` returns, so every branch runs
  on the state the lock protects?
- **PoC test**: `RUN_AT`-style hook is per step inside `migrate`, not before the lock; a test can
  instead take the directory lock in the test thread, start the open on another thread (it fails
  immediately with "another process is migrating"), so the TOCTOU needs the flags read before
  the lock and the files changed after: expose the two halves (`classify(path)` and the locked
  match) or re-stat under the lock and assert on a directory holding `tn-lmdb.dat` + marker that
  the error is never `both_engines` whatever was stat'ed before.
- **Proposed fix**: take the lock first when either `mdbx.dat` or the temp directory exists,
  then stat the three names again (two `symlink_metadata` calls) and match on those. Migration
  path only.
- **Relevant Files**: `crates/tn-reth/src/env/database/migrate.rs`
- **Source**: T3

### T3-5. `db reset-execution` resume: the "run the reset again in a second" advice cannot work, and the other `db` commands do not notice a `.partial`
- **Severity (initial)**: Informational
- **Category**: Error Handling / Docs
- **Location**: `crates/telcoin-network-cli/src/db/reset_execution.rs:172-174`,
  `crates/telcoin-network-cli/src/db.rs:166-178` (`migrate-execution`), `:210-224`
  (`stats`, `check`)
- **Claim**: when a `.partial` is being resumed its final name is fixed by the partial's stamp,
  so if `execution-reset-<stamp>` also exists (only by hand: the final rename is atomic) the
  error "already exists: run the reset again in a second" sends the operator in a loop; the
  message should say to move or rename one of the two. `db migrate-execution`, `db stats` and
  `db check` do not call `refuse_interrupted_reset`: with `db/` already moved into the
  `.partial`, `migrate-execution` prints "nothing to migrate: no MDBX database" and `stats`
  "no reth database", both true of the datadir root but not of the datadir's state.
- **Failure scenario**: operator interrupts a reset, runs `db stats` to see what the datadir
  holds, reads "no reth database at …/db", and concludes the database is gone.
- **Key Question**: should every `db` command that names `db/` refuse (or at least mention) an
  unfinished reset, as the node and `load-state` do?
- **PoC test**: `reset_execution::tests`: create `execution-reset-X.partial/db` and
  `execution-reset-X`, run `reset_execution(root, true)`, assert the error names both directories
  and does not say "in a second". For the commands: a `.partial` holding `db`, run `db stats`,
  assert the error mentions the unfinished reset.
- **Proposed fix**: in the resume case, bail with "both `<partial>` and `<target>` exist: move
  one aside"; call `refuse_interrupted_reset` at the top of `stats`, `check` and
  `migrate-execution` (one line each, after `PidLock`).
- **Relevant Files**: `crates/telcoin-network-cli/src/db/reset_execution.rs`,

- **Source**: T3

## Considered and rejected
- **The heal removes static files past genesis.** `holds_only_genesis` (layout.rs 203-214)
  checks all six segments' highest block against the genesis number before `block_hash(0)`;
  `delete_segment` is reached only when both hold. Holds.
- **A stop inside the heal is lost.** Headers last (222-227); sidecars without a data file are
  invisible to `iter_static_files` and emptied on recreation (`create_or_open_files` 149-170,
  `ChangesetOffsetWriter::new` with `committed_len` 0). Holds.
- **A v2 datadir opens as v1 after losing `storage_settings`.** The marker refuses it
  (`existing` 307-313); the row and the checkpoints share genesis's transaction (init.rs
  203-264); no `db` command touches `Metadata`. Holds.
- **The heal uses the marker's layout vs the request.** `create(factory, requested)` after the
  files are gone; the marker is overwritten; on the MDBX build `requested` is always v1. Holds.
- **`existing` writes the v1 marker before `refuse_v2_segments`** (321-331): a v0.16.0 datadir
  whose static files are another v2 datadir's gets its (correct, v1) marker and is then refused;
  swapping the right static files back opens. No harm.
- **`db_tip` is the Headers stage checkpoint: does TN advance it?** `save_blocks` writes the
  stage checkpoints in the block's transaction; `env/mod.rs` test
  `test_startup_heals_static_files_ahead_of_database` 699-704 asserts the Headers checkpoint
  moves with the commit. Holds.
- **Static files removed beside a database at genesis.** `(Some(0), None)` → `existing` →
  `check_consistency` finds nothing to unwind (0 vs 0) → `init_genesis_with_settings` finds no
  genesis in static files and writes genesis again over a database that holds it: the writes
  are upserts or appends to empty jars; for v1 `insert_genesis_state` appends the genesis
  reverts to `AccountChangeSets` under an existing key, which MDBX/tn-lmdb refuse or accept
  (append of an equal dup) — a datadir that never left genesis, and the only outcome is a
  refused start. Not a finding.
- **Database ahead of the static files (static files swapped from an older datadir, or
  removed, with a chain in the database).** `init_provider_factory` 479-493 refuses on the unwind
  target. Holds (and T3-3 asks for the README row).
- **Another chain's static files.** `init_genesis_with_settings` reads block 0's hash from the
  static files and refuses `GenesisHashMismatch` (init.rs 150-180). Holds.
- **`TN_LAYOUT_VERSION` written after data.** The marker's transaction commits before genesis
  (`create`, 290-292), and on an existing datadir before any read through the cache. Holds.
- **`database.version` left at 2 on a tn-lmdb datadir with data.** Only in the migration window
  before 711, with `mdbx.dat` still present; `finish`'s stat check covers the old binary's
  writes there; `record_db_version_file` rewrites 2 → 1002 at every later open. Holds.
- **Old binary vs each new file.** Traced in Q2: the version file stops it before any file is
  opened; unknown segment names and `.csoff` are skipped by `parse_filename` in any case.
- **The `StorageSettings` JSON shape between reth v1.11.3 (old binary) and v1.11.4
  (vendored).** One field, `storage_v2: bool` (metadata.rs 16-27); a v0.16.0-adiri row parses.
  Holds.
- **Migration state table rows vs code.** All eight match (Q3).
- **`finish` removes `mdbx.dat` after the old binary ran on it.** Refused by the stat record
  (969-972; test `mdbx_written_after_the_commit_point_is_refused` covers an append and a touch).
  The case it does not cover is T3-1.
- **The rename's durability at the commit point.** Rename → `fsync_directory(path)` (704-707)
  before the version file; a crash before that fsync can put `tn-lmdb.dat` back in the temp
  directory, which the next open reads as "stopped before the commit point" and migrates again.
  Holds.
- **`migrate_reth_db` returns without `record_db_version_file` when nothing is pending** (350):
  a pre-tripwire tn-lmdb `db/` keeps 2 until the node opens it; the node's open rewrites it.
  Pre-release datadirs only. Holds.
- **Free-space check uses `db/`'s filesystem.** `free_bytes(path)` with `path` = `db/`, which
  exists when `mdbx.dat` does. Holds.
- **`db stats`/`db check` on `(no,yes,no)` + emptied temp directory.** They open a complete
  `tn-lmdb.dat` read-only; the README promises that refusal for `load-state` only. Not a
  finding.
- **The reset's `PidLock` leaves `telcoin.pid` in the datadir.** By design (the lock file is
  the datadir's); the test at 262-270 pins the listing.
- **`blobstore/` kept by the reset.** reth's pool blob store holds pool sidecars keyed by tx
  hash, not chain data; stale entries are harmless. Matches the README.
- **A symlinked `db/` or `static_files/`.** `symlink_metadata` counts the link; `rename` moves
  the link, not the target, so the moved-aside entry stays a link to the live data and the
  rebuild creates a real `db/`. Unusual setup, documented nowhere, no claim broken.
- **Restore writes the wrong layout.** `open` goes through `RethEnv::new` with
  `RethConfig::new`'s `for_new_datadirs()`; `storage_layout_tests::snapshot_restores_across_storage_layouts`
  restores each pack into each layout and reopens. Holds.
- **The floor marker survives a failed `load-state`.** `clean_created_chain_data` removes it
  last (db.rs 990-1010); a kill leaves it, and the rerun overwrites it (`write_restored_state_floor`
  rename). A node started on that datadir fails closed on the first pinned read below `B`.
  Holds.
- **`--version` names the layout.** It does not; no doc says it does. An operator checking a
  build before `db reset-execution` has only the start log line. Optional: add
  `Storage layout (new datadirs): v2` to `LONG_VERSION` from `StorageLayout::for_new_datadirs()`.
- **Format-freeze fixtures are opened in place.** `open_fixture` copies the tree into a temp
  dir first (628-643). Holds.
- **The `adiri` skip hides a writer regression.** The read-back test still runs on adiri; the
  writer test runs on the default build, which shares the storage code. Holds.
